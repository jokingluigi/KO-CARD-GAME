## 실제 동작

관리자 `/admin/shop-decks`에 상점 덱 관리 메뉴를 추가했다. 등록·전체 정보 수정·즉시 판매 중지·가격·정렬 순서를 지원한다. 카드명과 정확한 코스트로 기존 DB 카드를 검색하고 수량을 조절한다. 대표 이미지는 기존 Supabase/Replit Storage 어댑터의 독립 폴더 `uploads/shop-decks/`에 업로드하며 실제 파일 바이트를 검사한다. PNG/WebP/JPEG 최대 5MB를 지원하고, 이미지 크기·형식 검증은 기존 공통 디코더를 재사용한다. 원본 카드 이미지는 변경/삭제하지 않는다.

일반 덱 규칙은 기존 엔진의 `maxCardCopies` / `validateDeckCounts`를 재사용한다.

- 정확히 25장, Normal 3장/Epic 2장/Legendary 1장 제한, Legendary 전체 3장.
- WRESTLER/TECHNIQUE만 지원. 일반 토큰·챔피언 토큰·존재하지 않는 카드·DISABLED 정의는 금지.
- 비용 6 초과를 임의 제한하지 않는다. 기존 규칙상 기본 턴 골드 한도와 카드 비용은 별개다.
- 기본은 PUBLISHED 카드·챔피언만 판매한다. 관리자가 **미공개 판매 허용**을 명시적으로 체크한 경우에만 DRAFT를 포함한다. 기존 덱/대전은 소유한 DRAFT 카드 사용을 이미 허용한다. 이 정책을 바꾸지 않았다.
- 등록 이후 카드 희귀도·공개 상태·삭제 여부가 변하면 상점에 구매 불가를 표시하고 서버가 재검증한다. 잘못된 카드가 섞인 경우 상세 카드 데이터와 비공개 추천 챔피언 이미지를 노출하지 않는다. 판매 중지는 원본 참조가 깨져도 가능하다.

플레이어 상점 `/shop`에 카드팩 / 완성 덱 카테고리를 추가했다. 기존 팩 구매의 수량·재화·연출은 그대로다. 각 덱은 이름·설명·이미지·가격·25장 구성·수량·추천 챔피언·포함 여부·구매 여부를 표시한다. 구성에서 카드를 누르면 기존 `CardDetailDialog`가 열린다.

### 구매 정책

각 상품은 **계정당 1회** 구매한다. 최초 구매 영수증이 영구 재시도 키이므로 새 요청 ID나 재접속으로 다시 눌러도 이중 차감·재지급·중복 덱 생성이 없다. 구매 완료 후 해당 덱을 직접 삭제해도 구매 이력/카드 소유권은 유지한다. 재시도가 삭제한 덱을 다시 만들지는 않는다.

기존 카드 소유 모델은 `user_card_collections.quantity`다. 필요한 수량과 보유 수량의 차이만 지급하고, 이미 더 많이 가진 수량은 유지한다. 가격 할인·자동 환불·프리즘 교환은 하지 않는다.

추천 챔피언은 상품 안내다. **챔피언 함께 지급**이 설정된 상품만 실제 챔피언 소유권을 부여한다. 미포함 상품은 구매자가 보유한 챔피언을 선택할 수 있다. 미선택 시 보유한 추천 챔피언 → 다른 사용 가능한 보유 챔피언 순으로 선택한다. 보유 챔피언이 하나도 없으면 차감 전에 차단한다. 추천 챔피언을 자동 획득한 것처럼 표시하지 않는다.

기존 덱 API/DB에 슬롯 제한은 없다. 새 UUID로 기존 `decks`에 저장하고, 선택되어 있던 기존 덱은 건드리지 않는다. 40개 기존 덱이 있는 계정에서도 추가 저장·기존 덱 보존을 확인했다. 구매 덱은 이름 변경·구성 편집·저장·대표 덱 선택·삭제가 가능한 일반 덱이다.

## 원자성과 동시성

서버는 클라이언트 가격/카드 목록을 사용하지 않는다. 하나의 DB 트랜잭션에서 다음을 수행한다.

1. 상품 행 공유 잠금, 사용자 재화 행 갱신 잠금, 기존 구매 영수증 확인.
2. 판매 상태와 현재 카드 정의를 검사하고 해당 정의를 공유 잠금으로 보호.
3. 포함 챔피언 또는 실제 보유 챔피언 검증, 잔액 검증.
4. 기존 재화 차감. 기존 테스트 계정 무제한 정책은 그대로 재사용.
5. 보유 행을 일괄 확보하고 잠근 뒤 부족분 계산, `greatest(기존 수량, 필요한 수량)`으로 일괄 반영.
6. 명시적인 포함 상품에 한해서 챔피언 소유권 지급.
7. 기존 덱 테이블에 덱 생성, 영구 구매 영수증 저장, 기존 `currency_transactions`에 `SHOP_DECK_PURCHASE` 기록.
8. 커밋 후 결과 반환.

상품은 공유 잠금이므로 서로 다른 구매자끼리 상품 전체를 직렬화하지 않는다. 같은 계정의 여러 상품 구매는 기존 사용자 행 잠금으로 잔액을 보호한다. `(user_id, product_id)` 고유 인덱스도 중복을 막는다. 카드 획득을 별도 소유 모델로 우회하지 않는다. 부족분 기록을 읽기 전에 없는 보유 행도 확보해 팩 개봉과의 경쟁으로 영수증 수량이 부풀지 않게 했다.

DB 실패를 마지막 재화 원장 INSERT에 의도적으로 주입했을 때 재화·카드·챔피언·덱·영수증 모두 롤백된 것을 실제 API 경로에서 확인했다. 오류를 제거한 재시도는 정상 구매된다.

### 부하

- 플레이 중 전투 이벤트나 렌더링마다 신규 쿼리/쓰기 없음.
- 상점 덱 목록: 고정 5개 배치 조회 (상품/본인 영수증/본인 챔피언 + 관련 카드/추천 챔피언). 관련 ID가 없으면 마지막 두 조회를 생략한다.

- 구매: 일반 계정 기준 약 12~13개의 SQL문 (BEGIN/COMMIT 제외) (선택 챔피언/테스트 계정 정책에 따라 변동), 단일 트랜잭션. 카드 수에 따라 별도 INSERT를 남발하지 않고 일괄 처리한다. 동일 상품 재시도는 3개 조회 후 영수증 반환, 쓰기 없음.
- 신규 인덱스: 판매 상태/정렬, 사용자/상품 고유 구매. 구매 영수증은 계정당 상품별 한 행이다. 원시 전투 로그를 추가하지 않는다.
- 상점/관리자 카탈로그는 현재 기존 규모와 동일하게 목록을 일괄 로드한다. 수천 개 상품으로 확장한다면 페이지네이션을 추가할 수 있다. 그런 규모의 부하 시험은 하지 않았다.

`pnpm run build`의 전체 타입 검사·API 빌드·Vite 프런트 빌드도 통과했다. 처음 두 기존 DB 테스트를 한 프로세스에서 실행했을 때 각 after hook의 공용 pool 이중 종료가 발생하여, 기존 러너 방식대로 서로 다른 프로세스로 재실행했고 모두 통과했다. 제품 코드나 테스트 종료 검사를 무력화하지 않았다.

### 미실행/범위 한계

- 실제 물리 스마트폰: 미실행. 위 모바일 결과는 Chromium 터치 에뮬레이션이다.
- 실제 운영 Supabase Storage 업로드/CORS·DB 마이그레이션: 미실행. 실제 SDK를 로컬 HTTP 저장소에 연결해 검증했다.
- 수천 동시 구매 등 대규모 부하: 미실행. PostgreSQL의 실제 동시 요청 및 행 잠금만 검증했다.
- 새 구매 덱으로 타워 진행/보상을 별도 실행하지 않았다. 타워 전투·보상·덱 제한은 수정하지 않았다. 기존 엔진 회귀에 타워 엔진 검사는 포함된다.
- 구매 덱으로 AI/PvP 전체 경기 승리·보상까지 별도 플레이하지 않았다. 실제 전투 진입·카드 사용과 기존 엔진 회귀 범위를 구분했다.
- 원격 GitHub CI 결과는 PR의 실제 checks를 확인해야 한다. 로컬 결과를 원격 CI 통과로 표시하지 않는다.

## 재현

저장된 클라우드 설정의 Node 24와 pnpm 환경을 사용한다. 기존 DB/Storage 비밀키는 필요 없다. 각 러너는 DB/Storage 주소를 강제로 loopback으로 설정한다.

```sh
source /workspace/cloud-setup/env.sh
pnpm run build
node --import ./docs/qa/checkpoints/20261006/qa-loader.mjs --test --test-isolation=none lib/db/qa/shop-decks.test.ts
node docs/qa/shop-decks-browser-runner.mjs
```

네이티브 검사는 **로컬 전용** PostgreSQL `127.0.0.1:55432`, 사용자 agent, 유지용 DB `ko_cosmetics_qa`를 준비하고 `KO_SHOP_DECKS_NATIVE=1`로 같은 통합 테스트를 실행한다. 프로세스별 새 `shop_decks_qa_<pid>` DB를 생성/삭제하므로 운영 연결 문자열을 받지 않는다. GitHub의 전용 PostgreSQL17 서비스도 동일한 조건이다. 브라우저 러너는 임시 API5188/Vite5178을 띄우고 자신이 시작한 자식 프로세스만 종료한다. 로그·fixture는 추적하지 않는 `qa-results/shop-decks`에 생성된다. fixture의 로컬 계정 쿠키/암호는 커밋하지 않는다.

## 적용/복구 순서

1. 꾸미기 PR #59와 본 후속 PR을 검토한다. 자동 병합/배포는 없다.
2. 승인 후 기존 운영 DB의 백업/접근 역할을 확인하고 배포한다. 기존 시작 설치기가 추가 스키마 `0053`/`0054`를 advisory-lock 트랜잭션으로 적용하므로 **배포 승인은 이 추가 스키마 적용도 포함해야 한다**. 이 작업에서는 실행하지 않았다.
3. 운영 Storage에서 새 `shop-decks` 폴더의 서버 서명 업로드/읽기와 브라우저 CORS를 확인한다. 기존 서비스 비밀키를 GitHub/클라이언트에 넣지 않는다.
4. 실제 상품은 운영자가 등록한다. 테스트 상품·유저·재화·카드는 운영에 시드하지 않는다.
5. 문제 시 상품 판매 중지 후 코드 롤백. 기존 구매로 얻은 카드/챔피언/덱/재화 원장/영수증은 보존한다. 운영 테이블 DROP·구매 소유권 제거·자동 환불을 롤백 작업으로 실행하지 않는다. 빈 테스트 환경의 DDL 롤백과 운영 자산 복구는 구분한다.
