## 긴급 복구

마지막 정상 커밋 `ce5568d`를 API와 프런트에 즉시 재배포해 두 서비스의 `live`와 커밋을 확인했다. [API 복구](api-restore.json), [프런트 복구](front-restore.json).

## 재발 방지 구현

1. 두 운영 서비스의 기본 브랜치를 `main`에서 **`production`**으로 변경했다. 자동 배포는 끈 상태를 유지했다. main은 병합하거나 덮어쓰지 않았다.
2. **외부 승인 커밋 고정**: Render 빌드 명령 맨 앞에서 `RENDER_GIT_COMMIT`이 승인한 전체 SHA와 정확히 같은지 검사한다. 다르면 의존성 설치나 소스 빌드 전 실패한다. 이 명령은 배포되는 코드 안이 아니라 Render 설정에 저장된다. 오래된 커밋에 검사 파일이 없거나 검사 코드가 달라도 우회되지 않는다.
3. **안전 배포 실행기** `scripts/deploy/release.mjs`: 전체 커밋 SHA를 명시해야 한다. 현재 체크아웃, 보호된 최소 기준, 원격 production HEAD, 각 서비스의 현재 live 커밋을 확인한다. 현재 live를 포함하지 않는 이전·갈라진 이력은 거부한다. 다른 배포 진행 중에도 거부한다.
4. 실행기가 검증한 대상만 Render 설정에 승인한 뒤 배포한다. 성공 후 실제 공개 응답 버전까지 검사한다. 단순한 배포 상태 live만으로 완료 처리하지 않는다.
5. API `/api/healthz`는 `status`와 `revision`을 제공하고 캐시를 막는다. 프런트 빌드는 `/version.json`을 생성한다. 서버·프런트 커밋이 같은지 외부에서 확인할 수 있다.
6. `Production release safety` GitHub Actions를 추가했고 production 푸시에서 실제 실행·성공을 확인했다. [CI 기록](ci-runs.json).

최종 운영 설정과 배포 커밋, 공개 버전 확인은 [운영 검증](production-verification.json)을 기준으로 한다. `protected-settings.json`은 최초 단계의 설정 기록이며 최종 승인 고정 명령은 운영 검증 JSON에 기록된다.

첫 강화 버전 배포 중 API 빌드가 두 번 실패했다. 이때 복구한 정상 게임 버전은 계속 live였다. Render 로그 API가 403을 반환해 세부 빌드 실패 원인은 이 자료에서 확정하지 않는다. 최종 구현은 호스팅의 git 히스토리나 GitHub 조회에 의존하지 않는 외부 승인 SHA 검사로 변경했다. 최종 운영 빌드·버전 확인 결과는 위 기록과 구분한다.

## 한계와 운영 방법

GitHub production 브랜치의 강제 푸시/삭제 보호도 추가로 시도했으나 현재 토큰의 API 권한 부족(HTTP 403)으로 적용하지 못했다. 적용했다고 주장하지 않는다. Render 기본 브랜치 변경과 외부 승인 SHA 차단은 별개로 적용·검증한다.

Render 관리자 권한으로 빌드 보호 설정을 지우거나 저장된 과거 아티팩트를 강제로 롤백하는 행위까지 코드만으로 금지할 수는 없다. 관리자 권한 범위와 GitHub 브랜치 보호는 저장소/서비스 소유자 권한으로 추가 설정할 수 있다. 일반적인 기본 수동 배포와 안전 실행기에서는 구버전 소스가 다시 올라가지 않도록 막았다.

정상 배포 절차:

```sh
# 검증한 변경을 현재 production 위에 쌓고, force 없이 production에 푸시한다.
git push origin HEAD:production
# 전체 SHA를 명시한다. main이나 Render의 임의 이전 커밋을 배포하지 않는다.
NODE_USE_ENV_PROXY=1 node scripts/deploy/release.mjs api <전체_SHA>
NODE_USE_ENV_PROXY=1 node scripts/deploy/release.mjs front <전체_SHA>
```

수동 승인 없이 production 브랜치만 이동해도 승인 SHA와 다르면 빌드는 차단된다. 장애 시 임의의 과거 코드 재배포 대신, 원인을 수정한 검증 커밋을 현재 live 위에 쌓거나 별도로 승인한 복구 절차를 사용한다.
