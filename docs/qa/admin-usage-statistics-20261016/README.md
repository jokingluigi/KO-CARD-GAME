# 관리자 카드·챔피언 사용 통계 — 2026-10-16

## 구현과 집계 정책

실제 관리자 컴포넌트에 **사용 통계 → 카드 통계 / 챔피언 통계**를 추가했다. 경로는 `/admin/card-statistics`, `/admin/champion-statistics`이다. 목록·검색·정렬·50개 페이지·상세·일별 그래프·표본·최근 7일 비교·갱신/오류/빈 상태를 제공한다. 7/30/90일·전체 기간을 지원하며 기본은 30일이다. 게임 모드 필터·탭·랭킹·그래프 분리는 없다.

- 집계 단위: **서버에서 정상 종료가 확정된 실제 유저의 전투 참가 1건**. PvP 양측 유저, AI전 유저 측, 타워의 각 전투, 일반 드래프트의 실제 유저를 합산한다. 취소·진행 중·이탈 후 결과 미확정 기록은 포함하지 않는다. 서버가 승패를 확정한 항복·접속 이탈 패배는 종료 경기로 포함한다. 무승부는 별도 수이며 승률 분모는 승+패다.
- 날짜: 종료 시각의 UTC 날짜. 최근 N일은 오늘을 포함한 N개 달력일이고 오늘은 진행 중이다. 수집 시작 이전은 제외한다. 조회 종료 시각은 서버 현재 시각이다. 여러 지표는 하나의 REPEATABLE READ/READ ONLY 트랜잭션으로 읽고 각 SQL에는 5초 제한을 적용한다.
- 채용률: 해당 ID가 시작 덱에 있는 참가 수 / **시작 덱 확인 참가 수**. 중복 카드는 채용 참가 1건, 장수는 실제 장수. 시작 덱을 모르면 분모에서 제외하며 추측하지 않는다. 타워는 해당 전투 시작 덱 기준이며, 전투 후 획득 카드는 그 전투의 채용으로 소급하지 않는다.
- 손패 플레이: 실제 성공한 CARD_PLAYED/PLAY_FROM_HAND 이벤트 수. 취소된 루트 사용은 서버 관찰 체크포인트로 제외한다. 카드 사용의 비용·취소 동작을 변경하지 않는다. 클릭·실패·드로우·생성·자동 소환은 손패 플레이가 아니다. 같은 카드를 다시 사용하면 추가 횟수, 플레이한 참가 여부는 1건이다.
- 플레이율: 해당 ID의 성공 손패 플레이가 있는 참가 수 / 전체 유효 참가 수. 카드 승률은 **시작 덱 채용 승률**이며 플레이 경기 승률과 혼합하지 않는다. 고유 사용 유저는 플레이한 유저의 가명 식별자를 기간 내 정확히 중복 제거한다.
- 생성은 CARD_GENERATED, 필드 진입·소환은 ENTER_FIELD 이벤트로 측정한다. 귀속은 실제 카드 영역의 소유 유저 기준이다. 상대 효과로 유저 영역에 들어온 카드도 해당 영역 기록이다. 변신 자체를 별도의 손패 플레이·신규 필드 진입으로 만들지 않는다. 합체 시 실제 진입한 카드는 그 진입을 세고 기존 대상의 강화는 별도 소환으로 추가하지 않는다.
- 챔피언은 시작 시 선택한 ID를 보존한다. 실제 성공 능력 이벤트만 집계하고, 퀘스트 완료는 참가당 최초 한 번이다. 실제 엔진 완료 턴을 기록하며 평균 표시는 기존 전투 HUD와 같은 `matchTurnNumber`(양측 턴 한 묶음)를 사용한다. 퀘스트 적용 가능 분모는 해당 전투의 실제 퀘스트 존재 여부다. 퀘스트 없는 기록은 0%로 꾸미지 않는다. 완료/미완료 승률은 관찰 통계이며 인과 효과를 뜻하지 않는다.
- 카드·챔피언의 이름·효과·일러스트는 현재 DB 정의를 읽는다. ID가 같으면 통계는 유지된다. 삭제된 정의의 기록은 ID와 삭제 안내로 남기며 콘텐츠를 복원하지 않는다. 패치 일자를 임의로 생성하지 않는다.
- 기본 표본 안내: 10 미만 매우 적음, 30 미만 적음. 통계적 유의성 보장 기준이 아니다. 선택적 서버 환경 변수 `USAGE_STATS_VERY_SMALL_SAMPLE`, `USAGE_STATS_SMALL_SAMPLE`로 조정 가능하며 필수 신규 설정은 없다.

## 신뢰 경로와 제외 대상

클라이언트 횟수를 받는 수집 API는 없다. 조회 API는 `/api/admin/usage-statistics/cards`, `/champions`, 각각의 `/:id`이며 기존 세션 인증과 ADMIN 역할을 서버에서 검사한다. `/status`도 관리자 전용이며 수집 상태·RLS 상태만 반환한다. 이메일·사용자별 원자료·내부 가명 키는 반환하지 않는다.

1. PvP: 서버가 CAS로 저장한 최종 game state와 서버가 시작 시 고정한 덱/챔피언 스냅샷을 읽는다.
2. AI: 저장된 서버 시작 상태에서 행동을 서버 엔진으로 재실행한다. 확정된 요약을 일일 퀘스트 처리 전에 보관하므로 그 후의 퀘스트 저장 실패/서버 재시작도 복구한다. 최초 검증 요약은 덮어쓰지 않는다. 결과 보상의 기존 지급 방식은 변경하지 않는다.
3. 타워: 기존 전투 저장 UPDATE에 compact pending 요약을 함께 저장한다. 다음 전투가 currentBattle을 덮어써도 이 큐는 유지된다. 관리자 진단 run은 수집하지 않는다.
4. 드래프트: 실제 전투 진입 때만 시작 덱을 고정한다. 서버 관리자 경로에서 시작한 진단 여부를 보존한다. 기존 매칭 규칙은 유지한다. AI/NPC의 user binding은 없다.

기존 서버 예약 테스트 계정 두 개와 `usage_excluded_accounts`에 명시된 계정은 제외한다. 일반 ADMIN 역할 자체는 제외 사유가 아니다. 닉네임이나 클라이언트가 보낸 테스트 플래그를 사용하지 않는다. 로컬 fixture·개발 AI 시뮬레이션은 격리 DB/엔진에서만 실행하며 운영 경기 원본으로 저장하지 않는다.

서버 관찰 정보와 새 정의 ID가 상대의 숨겨진 카드 이벤트에 유출되지 않도록 기존 PvP sanitizer도 보완했다. 새 이벤트를 추가해 RNG의 이벤트 인덱스를 바꾸지 않고 기존 이벤트에 관찰 필드만 보탠다.

원본 종류+안정적인 경기 ID로 source key를 구성한다. source receipt와 참가·카드·일별 합계를 한 트랜잭션에서 저장한다. PK/UNIQUE가 경합·재전송·재시작을 막는다. 확정 이후 원본 정리 응답이 유실되어도 receipt를 재확인하고 체크포인트만 복구한다. 실패한 원본은 남기고 다른 원본의 집계는 진행한다. 로그에는 내용·이메일·토큰·키를 쓰지 않고 오류 코드와 원본 키의 축약 해시만 쓴다.

worker는 30초마다 실행하며 겹치지 않는다. 원본별 회당 최대 20건을 처리한다. 신규 미처리 전용 partial index로 처리한 모든 과거 경기를 반복 스캔하지 않는다. 실패/적체가 있으면 지연될 수 있으며 관리자에게 최종 갱신·실패 시각을 표시한다. 30일이 지난 **새 통계 원자료만** 회당 100개 참가 단위로 정리하고, 일별 합계·고유 유저용 최소 가명 키·멱등성 키는 보존한다. 기존 게임 기록은 삭제하지 않는다. 과거 구간과 전체 고유 유저도 합계를 더하는 근사법을 쓰지 않는다.

## 접근 보호와 운영 적용

새 통계 테이블 12개에 RLS를 활성화하고 클라이언트용 조회 정책을 만들지 않는다. 원자료가 저장되는 4개 경기 테이블에도 RLS를 활성화한다. 저장소의 데이터 접근은 기존 인증 API 경유이며 마이그레이션을 실행하는 API DB owner의 접근은 유지한다. 기존 DB 정책·계정 역할·관리자 권한을 변경하거나 확장하지 않는다. 적용 전 RLS 상태는 baseline에 보존한다. 별도 anon SQL 역할에 SELECT 권한을 주어도 새 통계 및 원본의 행을 볼 수 없는 것을 격리 DB에서 검사했다.

운영 적용은 사용자의 후속 “적용 및 배포도” 지시에 따라 진행한다. API 시작 시 기존 schema installation 트랜잭션 안에서 마이그레이션한다(기존 lock/statement timeout·advisory lock 유지). DDL은 반복 실행 가능하고 카탈로그 재시딩을 하지 않는다. 필요한 기존 설정은 DATABASE_URL과 기존 인증 설정뿐이다. 신규 제3자 분석 SDK·외부 개인정보 전송·운영 테스트 계정·운영 테스트 경기 생성은 없다.

롤백: 배포를 이전 커밋으로 돌리면 worker가 멈추고 추가 테이블/컬럼은 남겨 보존한다. 새 집계 테이블을 운영에서 삭제·초기화하지 않는다. 원본 RLS를 복구해야 한다면 baseline의 각 was_enabled를 확인한 후 그 상태로만 명시적으로 복구한다. 일괄 DISABLE RLS를 하지 않는다. 운영 적용/배포의 최종 커밋·공식 상태 API·HTTPS 파일 비교 결과는 PR에 기록한다.

## 과거 기록

저장 구조상 PvP 최종 상태/승패·챔피언 스냅샷, AI 시작 상태/처리 receipt, 타워 현재/최초 전투를 보관한다. 그러나 과거에는 시작 덱·정의 ID·취소 관찰을 이번 형식으로 고정하지 않았고 타워의 이전 전투가 덮어써질 수 있다. 과거 카드 사용·고유 능력 횟수의 일관된 복원을 보장하지 않는다. **과거 데이터 복원은 실행하지 않으며 새 수집 시작 이후 서버에서 확정된 경기만 표시한다.** 운영의 과거 사용자 경기 원자료를 전수 다운로드하거나 테스트에 사용하지 않았다.

실제 AI 서버 경로의 PLAY → 토큰 → 고유 능력 → 퀘스트 → 선택 취소 → 종료 → durable receipt → 관리자 API를 확인했다. 실제 타워 HTTP 종료 후 유저 측만 반영하고 반복 수집이 증가하지 않는 것도 확인했다. PvP는 서버 엔진 이벤트로 만든 영속 상태와 양측 유저 binding의 집계 통합 및 숨김 정보 회귀를 검사했다. **2개 브라우저의 PvP 실전·실제 휴대폰·운영 실사용 경기 생성·운영 부하 시험은 미실행**이다.

[성능 측정](performance.json), [검증 요약](validation.json), [브라우저 결과](browser-results.json). 스크린샷은 격리 PostgreSQL 호환 DB의 명시적인 검증 기록을 실제 관리자 컴포넌트로 렌더링한 것이며 운영 통계 예시 데이터가 아니다. 일러스트는 공식 리소스의 읽기 전용 사본이며 게임 원본을 변경하지 않는다.

## 비용·성능

공격마다 통계 INSERT를 하지 않는다. 타워는 기존 상태 UPDATE에 큐를 함께 저장하고, AI는 검증 종료 시 compact receipt 체크포인트 1회를 추가한다. 집계는 경기 종료 단위 batch다.

- 유저 1명 원본의 집계: 9 SQL 문(SELECT 2개 + 쓰기 문 7개), 하나의 트랜잭션. 카드별 insert/upsert는 묶는다. PvP 2명은 14 SQL 문. 유저 일별 중복 제거는 같은 INSERT CTE에 포함한다.
- 정상 원본당 처리 완료 체크포인트 UPDATE와 실패 항목 정리 DELETE가 추가된다(후자는 평상시 0행). worker idle 주기에는 원본 큐 4개 조회와 소규모 상태/정리 문만 실행한다.
- 관리자 목록: 데이터 SELECT 3개 + timeout SET 1개, 읽기 전용 snapshot 트랜잭션. 상세: SELECT 5개 + SET 1개. 기존 세션/점검 인증 조회와 트랜잭션 BEGIN/COMMIT은 별도다. 50개씩 반환하며 DB에는 일별 집계와 최소 고유 유저 키를 조회한다. 원시 전투 로그 전체를 API에서 재집계하지 않는다.
- 기간·카드/챔피언 ID·가명 유저·미처리 원본 인덱스와 쿼리 계획을 격리 DB에서 확인했다. 1,000 참가/참가당 카드 25개 기준 시간·공간은 첨부 JSON의 실제 측정값을 참고한다. 이는 PGlite 측정이며 Render/Supabase 실제 부하 보장 수치가 아니다. 카드 ID 길이·날짜 분산·유저 수에 따라 저장량이 달라진다.
