## 통합 시 추가 수정

- snapshot 전체를 캐시하면 JOIN 때 새로 추가된 상대 외형이 다른 프로세스에 남을 수 있다. SQL에서 `snapshot - 'cosmetics'`로 불변 도감만 캐시하고, 실제 잠긴 세션 행에서 작은 cosmetics를 매번 투영한다. 전투 상태/인증/버전/보상은 캐시하지 않는다.
- 버전이 같아도 이미지 이모티콘은 독립적으로 전달돼야 한다. 작은 `DRAFT_HEARTBEAT`에도 유효한 이모티콘을 넣고 클라이언트가 중복 제거해 렌더링한다. 전투 버전/판정은 변경하지 않는다.
- 실제 HTTP 테스트에서 입장 전 도감 캐시를 채운 뒤 JOIN하고 양쪽 외형이 맞는지 검사했다. 양쪽 같은 버전 heartbeat에서 이미지 전달도 검사했다. 실제 두 브라우저에서도 양방향 이미지 전달/새로고침을 확인했다.

## DB와 복구

0053/0054의 **추가 테이블 6개**(cosmetic_items, user_cosmetics, user_equipped_cosmetics, cosmetic_audit, shop_decks, shop_deck_purchases), 인덱스와 RLS를 기존 startup 트랜잭션으로 적용한다. 기존 카드/챔피언/소유권/덱/재화 데이터를 삭제·초기화하거나 콘텐츠 seed를 재실행하지 않는다. 테스트 상품/꾸미기/계정은 운영에 만들지 않는다. 실제 상품·스킨 등록과 지급은 관리자가 이후 진행한다.

롤백은 이전 운영 커밋 `5b3e547f820f485699721f6d15d43b65a802d83e`의 API/웹 코드를 다시 배포한다. 신규 테이블과 실제 발생한 구매·장착 기록은 보존하며 되돌리기 위해 테이블을 삭제하지 않는다. 배포 후 관리자 및 로그인 계정의 읽기 전용 API, 비로그인 차단, 공개 웹 로딩을 확인한다. 계정 로그인은 앞서 승인된 기존 관리자 계정만 사용한다.

동일 60초 입력의 통합본 DB 반환 행 UTF-8 페이로드: 대기 **32,520,826→329,467바이트**, 유휴 전투 **104,235,395→930,555바이트**. [통합 후 계측](egress-after-integration.json). PostgreSQL/TLS 프레이밍이나 Supabase 실제 청구값은 아니다. 운영에서 실제 감소량을 확정하려면 배포 이후 같은 부하/기간의 Shared Pooler Egress를 비교해야 한다.

운영 적용 전 읽기 전용 확인: 카드 **163개**, 챔피언 **11개**. 내용 해시는 [배포 전 기록](production-before.json)에 있다. 운영 콘텐츠가 작업 중 관리자가 수정되면 사후 해시 차이는 별도 확인이 필요하다.

배포 커밋·Render 상태·사후 확인은 배포 완료 후 별도 기록한다. 이전 각 기능의 상세 보고서는 과거 시점의 ‘배포 전’ 상태를 보존한다.
