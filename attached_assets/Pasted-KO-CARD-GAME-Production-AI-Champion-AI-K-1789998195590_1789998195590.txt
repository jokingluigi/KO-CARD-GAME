KO CARD GAME Production 관리자 페이지에
"AI 효과 생성 도우미"를 구현해줘.

중요:
이 기능은 자연어로 카드/Champion 효과를 입력하면 AI가 현재 KO CARD GAME의 실제 효과 엔진에서 사용할 수 있는 STRUCTURED Effect DSL로 변환해주는 관리자 전용 도구다.

단, AI가 Production DB를 직접 수정해서는 안 된다.

반드시:

자연어 입력
→ AI 초안 생성
→ 서버 측 schema/engine validation
→ 관리자 미리보기
→ 관리자가 직접 [적용] 클릭
→ 그때 기존 Admin 저장 흐름에 반영

순서로 동작해야 한다.

==================================================

불필요하게 repo 전체를 탐색하지 말고 관련 부분부터 확인해라.

우선 조사 대상:

- Admin 카드 편집 화면
- Admin Champion 편집 화면
- 현재 카드 effect / ability 입력 UI
- CardEffect
- STRUCTURED effect DSL
- RuntimeAction
- StructuredTarget
- effect-registry
- effect-engine
- CardDefinitionReference
- definitionRef
- targeting / PLAYER_CHOICE
- condition 관련 타입
- 현재 Admin 저장 API
- 현재 인증/Admin authorization 방식

특히 현재 엔진에서 실제 지원되는:

- action
- target
- trigger
- condition
- values
- definitionRef
- count
- destination
- generatedModifiers
- aggregateStats
- queuedEffect

등을 코드에서 확인한 뒤 구현해라.

지원하지 않는 action이나 임의 JSON 형식을 새로 만들어내지 마.

==================================================
2. 절대 바로 저장하지 말 것
==================================================

[효과 생성]은 DB를 수정해서는 안 된다.

AI 결과는 오직 draft 상태로 유지한다.

관리자가:

[현재 효과에 적용]

버튼을 눌렀을 때만 현재 Admin form state에 넣는다.

그 후에도 기존 Admin의 저장 버튼을 눌러야 실제 DB 저장이 이루어져야 한다.

즉:

AI 생성
≠ DB 저장

AI 적용
≠ DB 저장

기존 Admin 저장
= DB 저장

이 구조를 반드시 유지해라.

==================================================
3. AI API는 서버에서만 사용
==================================================

AI API Key를 browser/frontend bundle에 절대 노출하지 마.

프론트에서 직접 AI provider API를 호출하지 마.

관리자 frontend:

POST /api/admin/effects/generate

같은 기존 API 서버 endpoint를 호출하게 한다.

Production에서는 반드시 상대경로:

/api/admin/effects/generate

를 사용해라.

절대로 frontend 코드에서:

https://ko-card-game.onrender.com/api/...

처럼 Production API origin을 hardcoding하지 마.

현재 Production frontend와 API가 별도 Render 서비스로 동작하고 있으며
/api Rewrite가 사용되고 있으므로 기존 authenticated Admin HTTP 흐름과 동일하게 상대경로를 사용해야 한다.

fetch에는 프로젝트의 기존 Admin authenticated request 방식을 재사용해라.

==================================================
4. 관리자 권한 필수
==================================================

/api/admin/effects/generate

endpoint는 반드시 기존 Admin 인증/authorization을 거쳐야 한다.

로그인하지 않은 사용자나 일반 사용자는 호출할 수 없어야 한다.

클라이언트에서 버튼을 숨기는 것만으로 끝내지 말고
서버에서도 관리자 권한을 검증해라.

==================================================
5. AI에게 아무 JSON이나 만들게 하지 말 것
==================================================

AI가 임의의 action 이름이나 임의 schema를 만들면 안 된다.

현재 repo의 실제 Effect DSL을 authoritative source로 사용해라.

가능하면 기존:

- TypeScript types
- Zod schema
- effect registry
- runtime action registry

를 재사용한다.

중복된 별도 effect specification을 만들지 마.

AI 출력은 반드시 structured JSON 형식으로 받아라.

예시일 뿐이며 실제 schema는 현재 repo 타입을 따라야 한다:

{
  "trigger": "ENTER_FIELD",
  "effects": [
    {
      "type": "STRUCTURED",
      "action": "DAMAGE",
      "target": "...",
      "values": {
        "amount": 2
      }
    }
  ]
}

AI 응답을 그대로 신뢰하지 말고
서버에서 schema validation을 수행한다.

==================================================
6. Generation 결과 validation
==================================================

AI 결과를 최소 다음 단계로 검증한다.

1. JSON parse 가능
2. 현재 Effect DSL schema와 일치
3. 존재하는 RuntimeAction인지
4. target이 해당 action과 호환되는지
5. 필요한 values가 존재하는지
6. 숫자값이 유효한 범위인지
7. definitionRef가 있다면 실제 CardDefinition을 찾을 수 있는지
8. PLAYER_CHOICE / targeting 구조가 현재 engine 규칙과 호환되는지
9. trigger가 실제 지원되는 trigger인지
10. 해당 CardType에서 사용할 수 있는 효과인지

검증 실패 시 Production 데이터를 수정하지 말고
관리자에게 이유를 보여준다.

예:

생성된 효과를 적용할 수 없습니다.

- SUMMON에는 유효한 CardDefinition reference가 필요합니다.
- "DESTROY_RANDOM_ENEMY"는 현재 지원되는 RuntimeAction이 아닙니다.

==================================================
7. 카드 참조 처리
==================================================

사용자가 자연어로:

"좀비를 하나 소환한다"

"기습 용병을 손에 생성한다"

같이 입력할 수 있다.

AI가 카드 이름 문자열을 게임 엔진에 그대로 hardcoding하지 않게 해라.

현재 DB/CardDefinition catalog를 이용해서
canonical CardDefinition ID / definitionRef를 사용해야 한다.

가능하면 AI generation context에 필요한 최소한의 카드 목록을 제공하거나,
AI 결과의 card name/reference를 서버에서 authoritative DB catalog와 매칭해서 canonical ID로 변환한다.

최종 structured effect에는 가능한 한:

definitionRef: {
  id: "<canonical CardDefinition ID>"
}

형태를 사용한다.

동명이인/애매한 카드가 있으면 임의 선택하지 말고
관리자에게 후보를 보여주거나 생성 실패로 처리한다.

==================================================
8. Token / generated card 주의
==================================================

Token도 CardDefinition 기반 구조를 유지한다.

특정 Token 이름을 effect-engine 코드에 hardcoding하지 마.

SUMMON / GENERATE는 기존 engine 규칙을 따라야 하며,
serializable CardDefinition 또는 올바른 definitionRef를 사용해야 한다.

현재 엔진의:

SUMMON requires a serializable card definition

validation을 삭제하거나 우회하지 마.

==================================================
9. 카드별 hardcoding 금지
==================================================

절대 다음처럼 구현하지 마:

if (card.name === "좀비") ...
if (card.id === "...") ...

AI 생성 기능은 generic 해야 한다.

새 카드가 추가돼도 코드 수정 없이:

DB definition
+
effect DSL
+
effect registry

만으로 사용할 수 있어야 한다.

==================================================
10. Prompt 구성
==================================================

AI에게 보내는 system/developer instruction에는
현재 KO CARD GAME의 effect DSL 규칙을 명확히 제공해라.

하지만 repo 전체 소스코드를 AI provider로 보내지 마.

필요한 최소 정보만 제공한다.

예:

- 지원 action 목록
- 지원 target 목록
- 지원 trigger 목록
- relevant schema
- 선택된 카드의 type
- 사용자가 작성한 자연어 설명
- 필요한 경우 CardDefinition 후보 목록

AI에게 다음을 명시한다.

- JSON만 반환
- 설명문 금지
- 지원되지 않는 action 생성 금지
- 게임 코드 생성 금지
- SQL 생성 금지
- 카드별 hardcoding 금지
- 모호한 요구는 unsupported/needsClarification으로 반환 가능

==================================================
11. AI Provider 구조
==================================================

Provider 호출은 server-side module로 분리한다.

예:

src/admin/effect-ai/...

또는 현재 프로젝트 구조에 맞는 위치.

API key는 환경변수에서 읽는다.

예:

OPENAI_API_KEY

단, 실제 프로젝트에 이미 AI provider abstraction이나 env naming convention이 있다면 그것을 재사용해라.

API key가 설정되지 않은 환경에서는 서버가 crash하면 안 된다.

관리자에게:

"AI 효과 생성 기능이 설정되지 않았습니다."

같은 명확한 오류를 반환한다.

Secret 값을 로그에 출력하지 마.

15. 모호한 자연어 처리
==================================================

AI가 추측으로 중요한 게임 규칙을 만들어내지 않게 한다.

예:

"강하게 만든다"

처럼 수치나 대상이 불명확하면:

{
  "status": "NEEDS_CLARIFICATION",
  "questions": [...]
}

같은 형태 또는 현재 구조에 맞는 안전한 결과를 반환할 수 있게 한다.

관리자 UI에서는:

"효과 설명이 모호합니다:
얼마나 강화할까요?"

등을 보여준다.

==================================================
16. 기존 효과 덮어쓰기 방지
==================================================

이미 카드에 효과가 존재할 경우
AI가 생성했다고 자동으로 기존 효과를 덮어쓰지 마.

[현재 효과에 적용]을 누르면:

- 기존 효과 교체
- 기존 효과 뒤에 추가

중 안전한 선택 UI를 제공하는 것이 좋다.

최소한 기존 효과가 존재하면
명확한 확인 없이 overwrite하지 마.

==================================================
17. Champion도 고려
==================================================

Card effect뿐 아니라 현재 Champion 시스템에서 사용하는:

- Champion ability
- Quest
- Quest reward/effect

중 기존 STRUCTURED DSL과 공유 가능한 부분이 있다면
같은 generator를 재사용할 수 있도록 구조를 generic하게 만들어라.

단, 이번 작업 때문에 Champion 시스템 전체를 refactor하지 마.

우선 기존 Admin 카드 효과 생성에서 안정적으로 동작하게 만들고,
Champion 편집 화면에 쉽게 재사용할 수 있는 컴포넌트/API 구조로 작성해라.

20. 테스트
==================================================

최소 다음 케이스를 테스트해라.

A.
입력:
"등장: 적 챔피언에게 2 피해"

기대:
현재 engine에서 지원하는 올바른 structured effect 생성.

B.
입력:
"자신에게 +2/+3"

기대:
올바른 BUFF 형태.

C.
입력:
"좀비를 하나 소환"

기대:
존재하는 좀비 CardDefinition을 canonical definitionRef로 resolve.
없는/애매한 경우 임의 ID 생성 금지.

D.
지원하지 않는 action 요구

기대:
validation 실패 또는 clarification.
DB 변경 없음.

E.
AI가 malformed JSON 반환

기대:
서버 오류로 안전하게 처리.
Admin 페이지 crash 금지.

F.
AI가 존재하지 않는 action 반환

기대:
schema validation에서 거부.

G.
AI API key 없음

기대:
서버 전체 crash 금지.
관리자 UI에 설정되지 않았다는 메시지.

H.
일반 사용자 API 호출

기대:
403 또는 기존 Admin authorization 정책에 맞는 거부.

I.
기존 효과가 있는 카드

기대:
자동 overwrite 없음.
