==================================================

현재 KO CARD GAME의 목표는:

→ AI가 게임 규칙을 이해

1. 현재 실제 Provider 문제
==================================================

이전 실제 Provider smoke에서:

READY:
A
D
F
G
H

등은 성공했지만

B
C
E
I
J

같은 케이스는 반복 실패했다.

주요 실패 원인:

- provider가 sourceId를 직접 생성
- malformed EFFECT structure
- provider schema와 validator expectation 불일치
- runtime AST와 structured output schema가 미묘하게 다름

이 문제를 해결한다.

==================================================
PART A — sourceId를 AI가 생성하지 않게 한다
==================================================

현재 가장 중요한 원칙:

현재 수정 중인 CardDefinition / ChampionDefinition의 source identity는
이미 서버가 알고 있다.

AI가 sourceId를 "추측"하거나 "생성"하면 안 된다.

==================================================
2. 서버 Context Injection
==================================================

generate request에는 서버가 이미 아는:

- current card definition id
- current champion definition id
- source entity type
- 필요 시 card type
- 현재 저장된 effect context

를 안전한 compile context로 제공한다.

Provider가 최종 AST에서 sourceId를 직접 만들어야 하는 구조를 제거한다.

==================================================
3. AI Output에서 sourceId 제거
==================================================

가능하면 provider-facing structured schema에서
sourceId를 required field로 두지 않는다.

AI는 effect semantics만 생성.

그 뒤 서버 canonicalization 단계에서:

validated AI AST
+
trusted server context

를 합쳐
최종 executable AST를 만든다.

==================================================
4. Provider가 sourceId를 보내더라도
==================================================

legacy/provider hallucination으로
sourceId가 포함될 가능성이 있다면:

절대 그대로 신뢰하지 않는다.

정책:

- reject unknown field
또는
- canonicalization 단계에서 제거

둘 중 authoritative schema 전략에 맞는 방식을 선택.

AI가 보낸 sourceId로
다른 카드/Champion effect를 수정할 수 없어야 한다.

==================================================
5. Security Regression
==================================================

TEST SRC1

Card A 편집 중.

Provider output에
sourceId = Card B

가 포함됨.

기대:

Card B에 적용되지 않음.

최종 executable AST의 source context는
Card A.

==================================================

TEST SRC2

Provider가 sourceId를 생략.

기대:

정상 compile 가능.

server가 Card A context 주입.

==================================================
PART B — authoritative schema 하나로 통일
==================================================

현재 의심되는 핵심 문제:

Provider output schema
Validator schema
Runtime AST schema

가 서로 조금씩 달라
Provider가 "형식상 그럴듯한 JSON"을 내도
validator/runtime에서 실패한다.

이걸 하나로 정리한다.

==================================================
6. Single Source of Truth
==================================================

가능하면 하나의 authoritative typed schema를 기준으로:

1. Provider structured output schema
2. Server validator
3. Canonicalizer
4. Runtime AST type
5. Admin mechanic plan reconstruction

가 파생되도록 정리한다.

동일 node type을
서로 다른 파일에서 수동으로 중복 정의하지 마.

==================================================
8. malformed EFFECT 문제
==================================================

실제 실패했던 provider output을 fixture로 저장/재현.

확인:

- provider schema가 너무 느슨해서 invalid shape 허용?
- validator가 provider schema보다 엄격?
- runtime type이 validator보다 다름?
- nullable/optional field mismatch?
- array/object shape mismatch?
- oneOf/discriminated union ambiguity?
- nested EFFECT wrapper 중복?
- action node와 effect container 혼동?

근본 원인을 수정.

==================================================
9. Canonicalizer
==================================================

AI output을 곧바로 runtime AST로 쓰지 말고
필요한 최소 normalization을 한다.

예:

- trusted source context 주입
- optional default 정규화
- legacy alias 정리
- 불필요 field 제거

단:

잘못된 의미를 추측해서
완전히 다른 effect로 "자동 수정"하면 안 된다.

semantic ambiguity는 FAIL로 반환.
