만약 현재:

MATCH_FOUND
→ 즉시 client game entry

구조인데 server runtime 준비가 비동기라면

4. runtime registration race 확인
==================================================

반드시 확인:

match DB row가 생성된 직후
runtime registry가 아직 없는 짧은 구간이 존재하는지.

예:

DB:
match ACTIVE

but

runtimeRegistry.get(matchId)
→ undefined

이 순간 WS가 연결되면 현재 server가 무엇을 하는지 확인.

- socket close?
- error?
- unauthorized?
- match not found?
- retry later?
- silent failure?

이게 실제 root cause라면
runtime이 준비되기 전에 client를 READY로 보내지 말 것.

==================================================
5. WS ticket timing 확인
==================================================

다음 상황 확인:

ticket이 너무 일찍 발급되는가?

ticket 발급 당시:

- match exists?
- runtime exists?
- user membership exists?
- room initialized?
- server can immediately accept socket?

확인.

또한 ticket이:

single-use
expiration
consumed on failed handshake

특성을 갖는지 확인.

첫 연결 실패 후 client가 같은 ticket을 재사용하고 있다면 수정.

필요한 경우 reconnect마다 fresh ticket 사용.

인증 완화 금지.

11. reconnect delay도 함께 확인

재연결이 빠르게 이루어져야 한다.

현재 reconnect timer/backoff를 확인.

다음과 같은 문제 검사:

- 첫 retry가 너무 늦음
- 고정 30초 timeout
- 60초 timeout
- exponential backoff가 과도함
- timeout 완료까지 다음 시도를 안 함
- failed socket이 완전히 닫히기 전까지 기다림
- stale timer가 남아있음

backend가 준비되면
다음 retry에서 즉시 붙어야 한다.
