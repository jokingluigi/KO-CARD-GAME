KO CARD GAME — CRITICAL QUEST PROGRESS REPAIR + FLEXIBLE QUEST ENGINE / ADMIN QUEST BUILDER V2

현재 문제는 두 가지다.

1. 실제 플레이를 해도 퀘스트 진행도가 오르지 않는다.
2. Admin에서 만들 수 있는 퀘스트 종류가 너무 한정되어 있다.

이번 작업은 기존 몇 개 Quest type을 하나씩 추가하는 작업이 아니다.

목표:
A. 일반 사용자 계정에서 실제 canonical gameplay event를 기준으로 Quest progress가 다시 정상적으로 올라가게 한다.
B. Admin이 카드/Champion 이름별 하드코딩 없이 다양한 조건의 Quest를 자유롭게 만들 수 있는 generic Quest Engine + Quest Builder를 만든다.

중요:
"퀘스트 종류 enum 몇 개 더 추가"로 끝내지 말 것.
앞으로 새로운 Quest를 추가할 때 runtime 코드 수정 없이
Admin 설정만으로 만들 수 있는 구조가 목표다.

==================================================
0. 절대 원칙
==================================================

- Quest progress는 Admin 계정 전용이면 안 됨.
- 일반 로그인 사용자의 실제 gameplay가 source of truth.
- client가 progress 숫자를 임의 제출해서 서버가 믿으면 안 됨.
- Action → Event → Quest Evaluation → PlayerQuestState.
- 같은 이벤트 replay/reconnect로 중복 progress 금지.
- 카드/Champion 이름 hardcode 금지.
- 특정 Quest ID hardcode 금지.
- eval / new Function / arbitrary JS 금지.
- Production 사용자 Quest 진행도 직접 수정 금지.
- Production QuestDefinition 임의 수정 금지.
- RLS 전체 disable 금지.
- 일반 사용자에게 Admin role 부여로 해결 금지.
- push 요청 없으면 push 금지.
- force push 금지.

==================================================
1. 가장 먼저 현재 Quest progress가 안 오르는 ROOT CAUSE 추적
==================================================

실제 일반 사용자 계정 기준으로 다음 경로를 trace:

Game Action
→ canonical Event emitted
→ Quest event ingestion
→ active QuestDefinitions load
→ condition matcher
→ qualifying delta 계산
→ dedupe
→ PlayerQuestState update
→ DB persistence
→ API/WS response
→ client query/cache update
→ progress bar render

반드시 "처음 끊기는 지점(first failing layer)"을 특정한다.

가능성 예:

A. Quest progress endpoint가 requireAdmin
B. 일반 사용자의 player identity resolve 실패
C. AI Match/Online Match가 Quest service를 호출하지 않음
D. event type 이름 drift
E. sourceActionType/actionId가 소실
F. QuestDefinition parser가 old schema만 읽음
G. PlayerQuestState INSERT/UPDATE가 RLS로 막힘
H. quest event dedupe가 모든 새 event를 duplicate로 오판
I. eventId가 undefined라 저장 skip
J. progress update는 됐지만 client cache invalidation 실패
K. Admin/test helper에서만 직접 progress 적용
L. match result event만 서버에 있고 card/action events는 client-only
M. ACTIVE/PUBLISHED Quest filter가 잘못됨
N. 시간대/start/end 조건이 잘못되어 active quest 0개
O. normal user에게 Quest assignment row가 생성되지 않음
P. legacy Quest schema와 current matcher가 불일치

추측으로 UI만 고치지 말 것.

5. QUEST CONDITION DSL V2
==================================================

Admin이 자유롭게 Quest를 만들 수 있도록
strict declarative QuestCondition DSL을 만든다.

예시 개념:

{
  "event": "WRESTLER_RETIRED",
  "filters": {
    "owner": "SELF",
    "sourceActionType": "USE_CHAMPION_ABILITY",
    "cardType": "WRESTLER",
    "tagsAny": ["좀비"]
  },
  "progress": {
    "mode": "COUNT",
    "amount": 1
  },
  "required": 7
}

실제 필드명은 현재 architecture에 맞게 설계.

중요:
runtime에서 exact Quest text를 파싱하지 않는다.
Admin이 저장한 validated structured condition을 실행.

==================================================
7. Progress Aggregation 지원
==================================================

단순 COUNT만 지원하면 또 한정된다.

최소 generic modes:

COUNT
→ qualifying event 수

SUM
→ event field 합산
예: 총 50 damage

SET_MAX
→ 한 번의 event/match에서 최고 수치
예: 한 번에 10 damage

DISTINCT_COUNT
→ 서로 다른 definition/tag/player/etc.
예: 서로 다른 선수 5종 사용

MATCH_COUNT
→ 조건을 만족한 match 수

WIN_COUNT
→ 조건을 만족한 승리 수

가능하면 현재 필요성과 architecture를 보고 구현.

임의 JS expression 금지.

SUM field는 whitelist된 numeric event fields만.

8. 대표적으로 만들 수 있어야 하는 Quest
==================================================

Admin 설정만으로 최소 다음 Quest들을 만들 수 있어야 한다.

Q1
"선수 카드를 10장 냅니다."
→ CARD_PLAYED
→ cardType WRESTLER
→ COUNT 10

Q2
"Technique를 5번 사용합니다."
→ TECHNIQUE_USED
→ COUNT 5

Q3
"상대 선수를 7번 리타이어시킵니다."
→ WRESTLER_RETIRED
→ victimOwner ENEMY
→ COUNT 7

Q4
"Champion Ability로 선수를 7번 리타이어시킵니다."
→ WRESTLER_RETIRED
→ sourceActionType USE_CHAMPION_ABILITY
→ COUNT 7

Q5
"좀비 태그 선수를 5장 냅니다."
→ CARD_PLAYED
→ cardType WRESTLER
→ tagsAny ["좀비"]
→ COUNT 5

Q6
"총 50 데미지를 줍니다."
→ DAMAGE_DEALT
→ SUM amount
→ required 50

Q7
"한 경기에서 3번 공격합니다."
→ ATTACK_RESOLVED
→ per-match scoped count 3
→ Quest progress policy에 맞게 match condition 완료 시 +1 또는 direct target 3
현재 schema에 맞게 generic하게 표현.

Q8
"AI Match에서 3승"
→ MATCH_WON
→ matchMode AI
→ COUNT 3

Q9
"온라인 대전에서 2승"
→ MATCH_WON
→ matchMode ONLINE
→ COUNT 2

Q10
"Legendary 카드를 3장 냅니다."
→ CARD_PLAYED
→ rarity LEGENDARY
→ COUNT 3

Q11
"생성된 카드를 5번 사용합니다."
→ CARD_PLAYED
→ isGenerated true
→ COUNT 5

Q12
"팩 10개를 엽니다."
→ PACK_OPENED
→ SUM packCount
→ 10

이 예시들은 테스트 fixture일 뿐
runtime에 이름별 switch를 추가하지 말 것.

9. COMPOSITE CONDITIONS
==================================================

Quest를 더 자유롭게 만들기 위해
AND / OR 조합을 지원.

예:

"온라인 대전에서 좀비 선수를 10장 낸다"

event CARD_PLAYED
AND
matchMode ONLINE
AND
cardType WRESTLER
AND
tagsAny ["좀비"]

또는:

"선수 또는 Technique를 총 20장 사용"

event CARD_PLAYED OR TECHNIQUE_USED

구조는 strict AST.

예:
allOf: [...]
anyOf: [...]

무한 중첩 방지.
max depth 설정.

10. per-match / lifetime progress scope
==================================================

Admin에서 조건의 집계 scope 설정 가능하게.

ACCUMULATE
→ 여러 경기 누적

PER_MATCH
→ 한 경기 안에서 목표를 달성해야 함

예:
"한 경기에서 5명의 선수를 리타이어"

PER_MATCH counter는 match end 시 조건 미달이면
그 match-local counter reset.

PlayerQuestState의 total progress와
ephemeral match progress를 분리.

47. 완료 조건
==================================================

1. 일반 사용자 실제 gameplay에서 Quest progress가 정상 증가.
2. Admin 권한이 progress에 필요하지 않음.
3. AI Match/Online canonical events가 Quest Engine에 도달.
4. replay/reconnect 중복 진행 없음.
5. Quest 완료/claim 정상.
6. QuestDefinition과 PlayerQuestState 권한 분리.
7. Admin이 코드 수정 없이 다양한 Quest 조건 생성 가능.
8. event + filters + aggregation + required를 generic하게 조합 가능.
9. card/Champion/tag 조건은 canonical refs/metadata 사용.
10. 특정 Quest/card/Champion 이름 runtime hardcode 없음.
11. 기존 Quest 호환 유지.
12. reward도 declarative하게 실행.
13. Normal User 보안/ownership 유지.
14. Production user progress/data mutation 없음.
15. 최소 3종 서로 다른 신규 Quest를 Admin UI만으로 만들어 실제 동작 증명.

핵심:
이번 작업의 성공 기준은
"퀘스트 몇 종류 더 추가"가 아니다.

앞으로 새로운 Quest 아이디어가 생겼을 때
개발자가 runtime 코드를 또 수정하지 않아도
Admin이 canonical event와 조건을 조합해
자유롭게 만들 수 있어야 한다.

그리고 그 Quest는 반드시
일반 사용자 계정의 실제 게임 플레이로 정상 진행되어야 한다.
