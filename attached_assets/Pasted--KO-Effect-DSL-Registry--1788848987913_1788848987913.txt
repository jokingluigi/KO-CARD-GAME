현재 KO 카드게임 관리자 페이지의 자연어 카드 효과 분석 시스템을 확장해줘.

목표:

관리자가 카드 효과를 자연어로 입력했을 때
기존 Effect DSL / Registry로 표현 가능한 효과는 그대로 자동 변환하고,

기존 시스템으로 표현할 수 없는 "완전히 새로운 메커니즘"이 등장하면
AI가 필요한 새로운 범용 Effect Module을 자동으로 설계하고,
자동 테스트까지 만든 뒤,
관리자의 승인을 받아 게임 엔진에 등록할 수 있게 한다.

중요:
새 카드마다 카드 이름을 하드코딩하는 구조를 만들지 마.

==================================================

1. 기본 흐름
   ==================================================

관리자가 카드 효과를 입력한다.

예:

"등장: 내 손패 선수들의 공격력을 서로 무작위로 섞습니다."

[효과 분석]

↓

먼저 기존 Effect DSL / Trigger / Action / Target / Resolver로
표현 가능한지 검사한다.

가능하면:

기존 시스템만 사용해서 Structured Effect 생성.

불가능하면:

"새 메커니즘이 필요합니다."

상태로 전환한다.

==================================================
2. 새 메커니즘 자동 제안
===============

AI가 필요한 범용 메커니즘을 분석해서 제안한다.

예:

신규 Effect Module:

SHUFFLE_STAT_VALUES

설명:

선택된 카드들의 특정 스탯 값을 서로 무작위로 재배치한다.

지원 가능 설정:

stat:
ATTACK / HEALTH / COST

targetFilter

owner

zone

count

randomSeed

등.

카드 이름이나 특정 카드 ID에 종속되지 않는
재사용 가능한 범용 기능으로 설계한다.

==================================================
3. AI가 생성해야 하는 것
================

새로운 메커니즘이 필요하면 AI가 최소 다음 항목을 생성 또는 수정할 수 있게 한다.

1. Effect Registry entry
2. Effect schema
3. Effect executor / handler
4. 필요한 Target/Value Resolver
5. validation 규칙
6. 자연어 Analyzer mapping
7. 관리자 Effect Builder UI 설정
8. TypeScript type
9. 자동 테스트
10. 필요한 Event Log 처리

단, 기존 기능이 이미 존재하면 중복 구현하지 않는다.

==================================================
4. 바로 라이브 적용 금지
===============

AI가 새 메커니즘을 만들었다고
즉시 운영 게임에 적용하지 마.

먼저 관리자에게 변경 내용을 보여준다.

예:

---

새 메커니즘 제안

이름:
SHUFFLE_STAT_VALUES

용도:
선택된 카드들의 특정 능력치를 서로 무작위로 섞음

추가/변경 파일:

* effectRegistry.ts
* shuffleStatValues.ts
* effectSchemas.ts
* analyzerMappings.ts
* shuffleStatValues.test.ts

게임 상태 영향:
currentAttack / currentHealth / currentCost 중 설정된 값만 변경

랜덤:
기존 deterministic RNG 사용

자동 테스트:
8 / 8 통과

기존 테스트:
142 / 142 통과

---

[새 메커니즘 적용]
[취소]

관리자가 [새 메커니즘 적용]을 눌러야 최종 등록되게 한다.

==================================================
5. 자동 테스트 필수
============

새 메커니즘을 생성할 때 반드시 해당 Effect에 대한 자동 테스트를 생성한다.

최소 테스트:

* 정상 실행
* 대상 없음
* 잘못된 대상
* 최대/최소 값
* 랜덤 효과라면 seed 재현성
* 게임 상태 손상 여부
* 기존 카드 효과와 충돌 여부

그리고 기존 전체 핵심 테스트도 실행한다.

새 테스트 또는 기존 테스트가 실패하면:

[새 메커니즘 적용]

버튼을 비활성화한다.

"테스트 실패로 적용할 수 없습니다."

라고 표시한다.

==================================================
6. 자동 백업 / 롤백
=============

새 메커니즘 적용 전에
변경 전 상태를 복구할 수 있는 안전한 checkpoint를 만든다.

적용 후 실제 문제가 발생할 경우
관리자가:

[이 메커니즘 비활성화]

또는

[이전 버전으로 되돌리기]

를 할 수 있는 구조를 만든다.

Effect Module마다:

id
version
status

를 관리한다.

status 예:

DRAFT
ACTIVE
DISABLED

==================================================
7. 절대 금지
========

다음 방식은 사용하지 마.

eval()

new Function()

DB에 JavaScript 문자열 저장 후 실행

사용자 자연어를 런타임에서 직접 코드로 실행

카드 이름 기반 if문

예:

if card.name === "나토마토"

같은 구조 금지.

새 메커니즘은 항상 실제 소스 코드의
정식 Effect Module로 생성되고
TypeScript 컴파일 및 테스트를 통과해야 한다.

==================================================
8. 기존 DSL 재사용 우선
================

AI는 새로운 Effect를 만들기 전에
반드시 기존 기능 조합으로 해결 가능한지 먼저 검사한다.

예:

SILENCE
+
DESTROY
+
LAST_DESTROYED_ATTACK
+
BUFF

로 가능한 효과라면
새로운 Effect Module을 만들지 않는다.

새 메커니즘 생성은
기존 시스템으로 표현할 수 없는 경우에만 사용한다.

==================================================
9. 메커니즘 중복 방지
=============

기존 Effect Registry에 비슷한 기능이 있다면
새 Effect를 또 만들지 않는다.

예:

SWAP_STATS가 이미 있는데
SWITCH_STATS라는 동일 기능을 추가하지 않는다.

Semantic similarity를 확인해서
기존 Effect 재사용을 우선한다.

관리자에게:

"기존 SWAP_STATS Effect로 구현 가능합니다."

라고 알려준다.

==================================================
10. 현재 게임 규칙 보호
===============

새 메커니즘을 생성할 때
다음 기존 게임 규칙을 임의로 수정하지 않는다.

턴
골드
드로우
보드 4칸
공격
리타이어
파괴
게임에서 제외
등장
퇴장
생성 카드
챔피언
챔피언 토큰
Target Selection
카드 Snapshot
deterministic RNG

Effect 구현에 필요한 최소 변경만 한다.

==================================================
11. 온라인 대전 대비
=============

새로운 Effect도 향후 온라인 대전에서
동일한 결과를 재현할 수 있어야 한다.

따라서:

* GameState에 직렬화 불가능한 객체 저장 금지
* Math.random 직접 사용 금지
* 브라우저 전용 상태를 게임 엔진에 저장 금지
* deterministic RNG 사용
* 같은 GameState + 같은 Action + 같은 seed면 동일 결과

원칙을 유지한다.

==================================================
12. 분석 결과 UI
============

관리자가 카드 효과를 입력했을 때 다음 세 상태를 명확히 구분한다.

A. 기존 시스템으로 구현 가능

✓ 기존 Effect 사용 가능

[효과 적용]

B. 새 메커니즘 필요

⚠ 새로운 범용 Effect Module이 필요합니다.

[메커니즘 생성]

C. 분석 불가

✗ 효과 의도를 충분히 이해하지 못했습니다.

관리자에게 문장을 수정하도록 안내.

억지로 코드를 생성하지 않는다.

==================================================
13. 메커니즘 생성 버튼
==============

새 메커니즘이 필요한 경우:

[메커니즘 생성]

버튼을 제공한다.

누르면 AI가:

* 구현 계획
* Effect 이름
* Schema
* Handler
* Analyzer mapping
* 테스트

를 생성한다.

완료 후 자동 테스트를 실행하고 결과를 보여준다.

그 다음에만:

[새 메커니즘 적용]

버튼을 활성화한다.

==================================================
14. 적용 후 자동 재분석
===============

새 Effect가 승인되어 Registry에 등록되면
처음 입력했던 카드 효과 문장을 자동으로 다시 분석한다.

예:

처음:

"등장: 내 손패 선수들의 공격력을 서로 무작위로 섞습니다."

↓

SHUFFLE_STAT_VALUES 생성/승인

↓

자동 재분석

↓

Trigger:
ENTER_FIELD

Effect:
SHUFFLE_STAT_VALUES

Target:
ALLY_HAND_WRESTLER

Stat:
ATTACK

↓

적용 가능

이 흐름으로 만든다.

==================================================
15. 재사용
=======

한 번 새로운 Effect가 등록되면
앞으로 비슷한 효과는 다시 코드를 생성하지 않고
기존 Effect를 사용한다.

예:

첫 카드:

"내 손패 선수 공격력을 서로 섞습니다."

→ SHUFFLE_STAT_VALUES 생성

이후 카드:

"적 필드 선수들의 체력을 서로 무작위로 섞습니다."

→ 기존 SHUFFLE_STAT_VALUES 재사용
→ stat = HEALTH
→ target = ENEMY_BOARD_WRESTLER

즉 시간이 지날수록 게임 엔진의 Effect Library가 확장되게 한다.

==================================================
16. 관리자에서 볼 수 있는 Effect Library
===============================

관리자 페이지에:

[Effect Library]

메뉴를 추가한다.

목록에서 다음을 확인 가능하게 한다.

Effect 이름
설명
버전
상태
사용 중인 카드 수
생성 날짜
마지막 수정일

예:

DAMAGE
BUFF
DRAW
ADJACENT_SUMMON
SHUFFLE_STAT_VALUES
COPY_CURRENT_STATS

각 Effect를 클릭하면:

* 어떤 역할인지
* 어떤 설정값을 받는지
* 어떤 카드에서 사용 중인지

확인할 수 있게 한다.

일반적으로 관리자 화면에서 Effect 코드를 직접 편집하게 하지는 않는다.

==================================================
17. 새 메커니즘 예시 테스트
=================

다음과 같은 기존 DSL에 없는 테스트 문장을 하나 만들어
전체 흐름을 검증해줘.

예:

"등장: 내 손패의 모든 선수 카드의 공격력을 서로 무작위로 섞습니다."

기존 기능으로 불가능하다면:

1. 새 Effect 필요 판정
2. SHUFFLE_STAT_VALUES 같은 범용 메커니즘 제안
3. 코드 생성
4. Schema 생성
5. 자연어 mapping 생성
6. 자동 테스트
7. 관리자 승인
8. Registry 등록
9. 원래 카드 문장 재분석
10. 실제 게임에서 정상 작동

까지 확인한다.

==================================================
18. 오류 처리
=========

AI 코드 생성 실패
컴파일 실패
테스트 실패
Effect validation 실패

가 발생해도:

게임 초기화
사이트 초기화
페이지 reload
기존 코드 자동 삭제

하지 않는다.

새 메커니즘은 DRAFT 상태로 남기고
기존 안정 버전을 계속 사용한다.

==================================================
19. 크레딧/작업량 절약
==============

불필요하게 프로젝트 전체를 분석하거나
대규모 리팩터링하지 않는다.

새 Effect 생성 시:

관련 Registry
관련 Handler
관련 Schema
관련 Analyzer
관련 Test

파일만 최소 수정한다.

기존 정상 코드를 다시 작성하지 않는다.

==================================================
20. 최종 완료 조건
============

최종적으로 관리자가 새로운 카드 효과를 자연어로 입력했을 때:

자연어 입력

↓

기존 Effect Library 검색

↓

기존 기능으로 가능
→ 자동 Structured Effect 생성

또는

기존 기능으로 불가능
→ AI가 새로운 범용 Effect Module 제안

↓

자동 구현

↓

TypeScript 검증

↓

자동 테스트

↓

관리자에게 변경사항 표시

↓

관리자 승인

↓

Effect Registry 등록

↓

원래 카드 효과 자동 재분석

↓

카드에 적용

이 전체 흐름이 가능해야 한다.

관리자는 새로운 메커니즘이 등장하더라도
가능한 한 직접 코드를 작성하지 않아도 되어야 한다.

다만 AI가 생성한 새로운 게임 엔진 코드는
반드시 테스트와 관리자 승인 이후에만 활성화한다.

기존 정상 게임 엔진을 불필요하게 대규모 리팩터링하지 마.
