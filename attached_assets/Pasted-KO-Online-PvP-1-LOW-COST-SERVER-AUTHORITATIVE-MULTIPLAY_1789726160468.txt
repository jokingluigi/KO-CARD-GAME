KO 카드게임에 Online PvP를 추가하기 위한

[1단계]
LOW-COST SERVER-AUTHORITATIVE MULTIPLAYER FOUNDATION

을 구현해줘.

이번 단계의 가장 중요한 목표:

"온라인 PvP 기반은 제대로 만들되,
초기 소규모 베타에서는 Replit 비용을 최대한 적게 사용한다."

현재는 소수의 Discord 테스터가 사용하는 초기 베타를 전제로 한다.

==================================================
0. 이번 단계에서 절대 과하게 만들지 마
==================================================

이번 단계에서 다음 인프라는 추가하지 마:

- Redis
- 별도 Matchmaking Server
- 별도 WebSocket Server Process
- 별도 Microservice
- Kafka
- Message Queue
- Worker Server
- Presence Server
- Analytics Server
- 별도 realtime database
- 매초 DB polling
- 매초 Match save
- 매초 Player presence save

현재 KO의 기존 Node/API Server 안에서
최소한의 Online Match 기능을 구현해.

초기 Production은:

Replit Autoscale
Maximum Machines = 1

운영을 우선 전제로 한다.

단 코드에 "인스턴스는 영원히 1개"라고 하드코딩하지 마.

향후 확장 가능성은 남겨둔다.

==================================================
1. 이번 단계의 실제 완료 목표
==================================================

두 명의 로그인 User가:

Player A
Player B

하나의 Online Match에 참가.

Client는:

"무엇을 하겠다"

라는 Action만 Server에 보냄.

Server가:

공식 GameState를 소유
↓
기존 KO Engine으로 Action 검증
↓
Action 실행
↓
Game Event 생성
↓
공식 GameState 갱신
↓
각 Player에게 필요한 정보만 전송

하는 구조.

온라인 UI / 예쁜 매칭 화면은 아직 만들지 않아도 된다.

==================================================
6. Active Match Runtime
==================================================

실제 ACTIVE Match는
Server memory에서 빠르게 처리 가능.

예:

Map<matchId, OnlineMatchRuntime>

Runtime:

matchId
gameState
snapshot
version
connections

하지만 Memory-only는 금지.

Server restart 시 복구 가능한
최신 serialized GameState가 DB에 있어야 한다.

==================================================
7. DB 비용 최소화
==================================================

매초 DB 저장 금지.

heartbeat마다 DB 저장 금지.

animation마다 DB 저장 금지.

turn timer tick마다 DB 저장 금지.

DB write는 실제 Game State가 변경되는
"성공한 Game Action" 중심으로만 한다.

권장:

Accepted Action 1회
→ Engine 처리
→ 최종 State 1회 atomic persistence

한 Action에서:

HP UPDATE
Gold UPDATE
Card UPDATE
Turn UPDATE

등을 별도 query 여러 번 발생시키지 마.

가능하면 serialized Match State를
한 번 업데이트.

==================================================
12. Action Envelope
==================================================

Online Action은 최소한 다음 구조.

{
  type: "MATCH_ACTION",
  matchId,
  requestId,
  expectedVersion,
  action
}

requestId:
중복 Action 방지.

expectedVersion:
stale client 방지.

==================================================
13. State Version
==================================================

GameState 변경 성공할 때마다:

version + 1

예:

18
→ Action
→ 19

Client는 currentVersion을 받음.

stale Action이면
안전하게 reject/resync.

==================================================
14. Duplicate Action 방지
==================================================

Double click이나 network retry 때문에
같은 Action이 2번 실행되면 안 된다.

requestId를 이용.

같은 requestId 재수신:

executeAction 재실행 X.

최근 requestId만
작은 in-memory cache로 유지.

끝없이 저장하지 마.

Match 종료 시 cleanup.

==================================================
15. Match별 Action 직렬화
==================================================

같은 Match에서
동시에 두 Action이 State를 수정하면 안 됨.

Per-Match queue/mutex 사용.

전역 lock 금지.

Match A 때문에
Match B가 기다리지 않아야 함.

==================================================

↓
Match ACTIVE인가
↓
해당 User 차례인가
↓
pendingSelection 상태인가
↓
legal action인가
↓
CardInstance가 실제 존재하는가
↓
Gold 충분한가
↓
target legal인가
↓

확인.

기존 Engine Validator / getLegalActions 재사용.
