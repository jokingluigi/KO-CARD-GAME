KO CARD GAME — UX FEATURE BUNDLE
1) ALT CARD INFO TOGGLE
2) DECK EDITOR SHOW UNOWNED + CRAFT FLOW
3) BULK CARD PACK OPENING

목표:
아래 3개 UX 기능을 한 번에 구현한다.

A. 카드 정보 보기:
ALT 키를 "누르고 있는 동안 표시"가 아니라
한 번 눌러 ON / 다시 누르면 OFF 되는 토글 방식으로 변경.

B. 덱 편집:
미보유 카드도 카드 목록에 표시.
미보유 카드를 누르면 덱에 바로 추가하지 말고
해당 카드의 제작 화면/제작 모달을 연다.

C. 카드팩:
팩을 한 개씩만 까는 방식 외에
여러 개를 한 번에 여는 Bulk Open 기능 추가.

중요:
기존 카드/인벤토리/덱 규칙과 충돌하지 않게
현재 구조를 먼저 조사하고 구현한다.

==================================================
1. ALT CARD INFO — TOGGLE 방식
==================================================

현재 동작이:
ALT keydown 동안만 상세정보 표시
ALT keyup 시 닫힘

이라면 이를 다음으로 변경:

ALT 1회 press
→ Card Info Mode ON

ALT 다시 1회 press
→ Card Info Mode OFF

즉:
hold-to-view가 아니라 toggle.

==================================================
2. ALT 키 이벤트 처리
==================================================

반드시 `keydown` edge에서만 토글.

브라우저 key repeat 때문에
ALT를 길게 눌렀을 때 ON/OFF가 빠르게 반복되면 안 됨.

예:

if (event.key === "Alt" && !event.repeat)
  toggle()

`keyup`에서는 상태를 바꾸지 않는다.

left Alt / right Alt 둘 다 같은 기능이면
현재 product convention에 맞게 처리.

==================================================
3. ALT 상태 UX
==================================================

Card Info Mode ON일 때:

- 기존 상세 정보/ALT Inspector 표시 방식 유지
- 마우스로 여러 카드를 이동해도 ON 상태 유지
- 다른 카드 hover/click 시 그 카드 정보 표시
- 덱 편집/컬렉션/게임 중 기존 지원 화면에서 동일하게 동작

OFF:
- 기존 일반 카드 표시

가능하면 화면에 작게:
`ALT 정보: ON`
같은 상태 indication 추가.

단 UI가 너무 복잡해지면
기존 스타일에 자연스럽게 녹일 것.

==================================================
4. ALT 토글 해제 조건
==================================================

다음 동작에서 토글 state를 어떻게 유지할지 현재 UX를 먼저 확인.

권장:
- route/page 변경 시 OFF로 reset
- modal 닫기 시 필요하면 유지
- input/textarea/select에 focus된 상태에서 Alt 단독 입력은
  브라우저/접근성 충돌을 피하도록 신중히 처리

특히 Alt+Tab, Alt+F4 등 OS shortcut에 간섭하지 말 것.

다른 키 조합:
Alt + 다른 key
→ Card Info toggle로 오인하지 않게 할 것.

가능하면 "Alt 단독 keydown" 기준.

==================================================
5. ALT 모바일/터치 회귀
==================================================

모바일에는 ALT 키가 없으므로
기존 tap/long-press/card info 접근 방식이 있다면 유지.

이번 수정으로 모바일 카드 정보 접근을 제거하지 말 것.

7. DECK EDITOR — 미보유 카드도 표시
==================================================

현재 덱 편집 카드 풀에서
owned quantity == 0인 카드를 숨기고 있다면
숨기지 말 것.

Deck Editor의 전체 카드 브라우저는:

- 보유 카드
- 미보유 카드

모두 보여준다.

단:
현재 deck-building format에서 사용 불가능한 카드
(예: token direct-add 금지 등)는 기존 규칙 유지.

==================================================
8. 미보유 카드 시각 표현
==================================================

미보유 카드:

- 카드 이미지/이름/비용/스탯/텍스트는 볼 수 있음
- owned count = 0 명확히 표시
- 약간 dim/locked styling 가능
- 하지만 읽기 어려울 정도로 가리지 말 것

보유/미보유 필터가 기존에 있다면:
- All
- Owned
- Unowned
같은 선택지를 제공할 수 있음.

필터가 없으면 강제 추가하지 않아도 되지만
검색/정렬과 충돌하지 말 것.

==================================================
9. 미보유 카드 클릭 동작
==================================================

owned quantity == 0인 일반 제작 가능 카드를 클릭하면:

덱에 추가 시도 금지.

대신:
해당 카드의 제작 화면/제작 모달을 연다.

Craft UI에는:
- 카드 이름
- 카드 이미지
- rarity
- 제작 비용
- 현재 보유 제작 재화
- 제작 버튼
- 취소/닫기

현재 기존 Craft screen/modal이 있다면 반드시 재사용.
새 중복 제작 시스템 만들지 말 것.

==================================================
10. 보유 카드 클릭 동작
==================================================

owned quantity > 0:

기존처럼 덱에 추가.

단 실제 덱에 이미 들어간 수량과
보유 수량/중복 제한을 검사.

예:
owned = 1
deck already contains = 1
→ 추가 불가
→ Craft option을 보여줄 수는 있음

현재 duplicate rule 유지.

==================================================
11. 제작 성공 후 Deck Editor 연계
==================================================

미보유 카드 클릭
→ Craft
→ 제작 성공

그 후:

- inventory quantity 즉시 갱신
- card tile owned state 갱신
- Deck Editor 전체 reload 없이 반영
- 가능하면 동일 카드가 선택된 상태 유지

자동으로 덱에 넣을지는 기존 UX를 따르되,
명시 규칙이 없다면:
제작 성공만 하고
사용자가 다시 클릭해서 덱에 추가하도록 하는 쪽이 안전.

자동 덱 추가는 하지 말 것.

==================================================
12. 제작 불가능 카드
==================================================

다음처럼 직접 제작할 수 없는 카드가 있을 수 있음:

- token
- special event-only
- unreleased
- disabled
- internal test card

이 경우:

미보유 카드로 보이더라도
Craft 버튼 대신
`제작할 수 없는 카드입니다`
같은 명확한 상태 표시.

임의로 제작 허용하지 말 것.

14. CARD PACK BULK OPEN
==================================================

현재 팩이 한 번에 1개만 열리는 경우
여러 개를 한 번에 열 수 있는 기능 추가.

지원 방식:

- 1개 열기
- 5개 열기
- 10개 열기
- 전부 열기

현재 inventory UX와 팩 보유량에 따라
버튼/드롭다운/수량 선택 중 자연스러운 방식 사용.

보유량보다 큰 수량은 선택 불가.

==================================================
15. Bulk Open 서버 처리
==================================================

중요:
클라이언트에서 `open pack` API를 N번 연속 호출하는 단순 loop보다
가능하면 서버에 canonical bulk-open API/action을 만든다.

예:
POST /api/packs/open
{
  packDefinitionId,
  quantity: N
}

정확한 endpoint/schema는 현재 프로젝트 convention 사용.

server가:

1. ownership/quantity 확인
2. pack N개 차감
3. 각 pack reward roll
4. inventory grant
5. result summary 반환

을 하나의 atomic/transactional flow로 처리.

==================================================
16. Bulk Open RNG
==================================================

현재 pack RNG/rarity odds 로직을 그대로 N회 재사용.

중요:
- bulk opening이라고 확률을 평균값으로 계산하지 말 것
- pack 10개면 "10개 각각" 독립적인 기존 pack roll semantics
- pity/guarantee system이 있다면 기존 순차 개봉과 semantic equivalence 유지
- deterministic/test RNG infrastructure가 있으면 재사용
- Math.random을 canonical gameplay/reward layer에 새로 도입 금지

==================================================
17. Bulk Open 원자성
==================================================

예:
10개 open 요청

중간에 4개만 처리되고 실패해서
팩 10개는 차감됐는데 보상 4개만 지급되는 상황 금지.

가능하면 transaction.

실패:
- pack quantity 차감 없음
- reward grant 없음

또는 기존 transaction architecture에 맞는 atomic guarantee.

==================================================
18. Bulk Open 중복 요청 방지
==================================================

버튼 연타/네트워크 retry로
같은 10-pack open이 두 번 실행되면 안 됨.

가능하면 requestId/idempotency key 사용.

UI:
opening 중 버튼 disabled.

==================================================
19. Bulk Open 결과 UI
==================================================

N개 팩 개봉 후 결과를 한꺼번에 볼 수 있게 한다.

예:

10 packs opened

Normal: 23
Legendary: 4
Champion: 3

그리고 실제 획득 카드 목록/수량.

동일 카드 여러 장이면
`Card X ×3`
처럼 aggregate 가능.

하지만 개별 pack 결과를 보고 싶다면
expander/detail로 확인 가능.

현재 animation이 있다면:
- "전부 스킵"
- 또는 bulk 전용 빠른 reveal
를 고려.

10팩을 10번 긴 애니메이션 강제 시청하게 하지 말 것.
