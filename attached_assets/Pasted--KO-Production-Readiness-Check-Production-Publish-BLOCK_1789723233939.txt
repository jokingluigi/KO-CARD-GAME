방금 수행한 KO Production Readiness Check 결과를 바탕으로
실제 첫 Production Publish 직전의 BLOCKER만 수정해줘.

아직 Publish 자체는 실행하지 마.

현재 보고된 NOT READY 항목 중:

- Production DB가 아직 없는 것
- Production URL이 아직 없는 것

은 실제 첫 Publish 이후에만 검증 가능한 항목이므로
이 두 항목 때문에 작업을 무한정 막지 마.

지금은 "Publish 전에 코드에서 해결 가능한 문제"를 먼저 모두 해결한다.

==================================================
1. Production ADMIN 계정 준비
==================================================

현재:

ADMIN_USERNAME=ADMIN
ADMIN_PASSWORD 존재
SESSION_SECRET 존재
ADMIN_EMAIL 없음

상태다.

Production에서 정상적인 관리자 계정을
안전하게 만들 수 있도록 정리해줘.

우선 기존 Auth / User / Role 시스템을 조사하고
기존 구조를 재사용해라.

권장 방식:

ADMIN_EMAIL 환경변수를 사용하는
idempotent Production Admin bootstrap.

조건:

- ADMIN_EMAIL
- ADMIN_USERNAME
- ADMIN_PASSWORD

가 모두 존재할 경우에만 동작.

Production DB에 해당 ADMIN이 없으면 생성.

이미 존재하면:
- 중복 생성 금지
- 일반 User를 무조건 덮어쓰기 금지
- 비밀번호 평문 저장 금지
- 기존 password hashing 사용
- role=ADMIN 서버측 권한 사용

매 서버 시작마다 계정을 새로 만들거나
비밀번호를 계속 덮어쓰면 안 된다.

더 안전한 기존 Production seed mechanism이 있다면
그걸 재사용해도 된다.

개발 DB의 TEST ADMIN을 Production으로 복사하지 마.

작업 후 나에게:

필요한 Production Secret 이름만 알려줘.
Secret 실제 값은 출력하지 마.

==================================================
2. Production Test Auth GET 경로 명시적 차단
==================================================

현재:

GET /__test/login/user
GET /__test/login/admin

이 실제 Test Login Route는 아니지만
SPA wildcard fallback 때문에 index.html 200을 반환한다.

Production에서는 이 두 경로가
명시적으로 404 또는 403을 반환하도록 수정.

중요:

이 차단 Route는 반드시
SPA /* fallback보다 먼저 처리되어야 한다.

예:

if production:
  GET /__test/login/user -> 404
  GET /__test/login/admin -> 404

Development + ENABLE_TEST_AUTH=true에서는
기존 Test Auth Helper가 정상 작동해야 한다.

이미 안전하게 차단되고 있는:

POST /api/test-auth/login

의 production protection도 유지.

Auth middleware를 약화시키지 마.

==================================================
3. Full-stack Production 배포 구조 확인
==================================================

KO는 Static-only site가 아니다.

현재 프로젝트 구조를 실제 코드 기준으로 조사해서
Replit Autoscale에서:

React frontend
+
API server
+
authentication
+
database

가 하나의 정상 Production 서비스로 동작하도록
Build / Start 구조를 확인해라.

특히 확인:

- production build command
- production start command
- API server entry point
- PORT
- 0.0.0.0 bind
- frontend static artifact serving
- SPA fallback
- /api/* 가 SPA fallback보다 먼저 처리되는지

절대로:

/api/foo
→ index.html

이 되어서는 안 된다.

==================================================
4. API와 Frontend 동일 Origin 우선
==================================================

현재 frontend가 상대 API path를 사용하고 있다면 유지.

Production에서는 가능하면:

https://KO_APP.replit.app/
https://KO_APP.replit.app/api/...

같은 동일-origin 구조로 동작하게 해라.

불필요하게 frontend와 API를
서로 다른 public URL로 분리하지 마.

기존 프로젝트가 이미 다른 올바른 배포 구조를 사용한다면
대규모 리팩터하지 말고 그것을 유지해라.

==================================================
5. Production DB 준비 상태 점검
==================================================

Production DB 자체는 아직 존재하지 않으므로
지금 실제 데이터 확인은 불가능하다.

대신 첫 Publish 시 필요한:

- schema
- migration
- DB connection configuration

이 준비되어 있는지 확인.

다음 테이블/모델이 migration 대상에서 빠지지 않는지 확인:

User
Session
Deck
Card Collection
Champion Ownership
Pack Inventory
Prism
Shop Currency
Card Skin

그리고 현재 사용 중인 기타 필수 KO persistent models도
실제 schema를 기준으로 확인.

임의로 새 DB 구조를 만들지 마.

==================================================
6. Production DB 초기화 원칙
==================================================

첫 Production DB 생성 시:

개발 DB 전체를 무조건 복제하지 마.

특히 복제 금지 대상:

- TEST USER
- TEST ADMIN
- test sessions
- test purchases
- debug-only data

반면 게임 운영에 필요한:

CardDefinition
ChampionDefinition
PackDefinition
AI Deck
Frame Definition
기타 canonical game content

가 DB 기반이라면
Production에서 어떻게 공급되는지 기존 구조를 확인.

필요하면 production seed/migration을 사용하되
TEST 계정 데이터와 분리.

==================================================
7. 첫 Publish 후 반드시 해야 할 검증 목록 작성
==================================================

코드 수정이 끝나면
실제 첫 Publish 이후 실행할
POST-DEPLOYMENT CHECK를 준비해라.

아직 실행하지 말고 체크 절차만 준비.

첫 Production URL이 생기면 반드시:

A. DATABASE
- Production DB 존재
- schema 적용
- 서버 재시작 후 데이터 유지

B. AUTH
- 일반 회원가입
- 로그인
- 새로고침 후 로그인 유지
- 로그아웃
- 다시 로그인

C. ADMIN SECURITY
- 일반 USER /api/admin/* -> 403
- 일반 USER /admin 접근 시 Admin 사용 불가
- Production Admin 정상 로그인
- /__test/login/user -> 404/403
- /__test/login/admin -> 404/403
- POST /api/test-auth/login -> 404

D. ROUTER
Production URL 직접 접근 + 새로고침:

/
 /shop
 /collection
 /decks

정상.

E. ASSETS
- Card artwork
- Card Frame
- Champion art
- BGM
- SFX

정상 응답.

F. CORE USER FLOW
회원가입
→ 로그인
→ Deck
→ AI Match
→ Match 종료
→ Main
→ Shop
→ Pack 구매
→ Pack 개봉
→ Collection 반영
→ 로그아웃
→ 재로그인
→ 데이터 유지

G. CONSOLE
치명적 Browser Console Error 없음.

10. 최종 결과
==================================================

이번 작업 후 결과는 두 단계로 보고:

PRE_PUBLISH_CODE_READY:
YES / NO

FIRST_DEPLOY_REQUIRED_FOR_REMAINING_CHECKS:
YES / NO

다음 항목별:

ADMIN_BOOTSTRAP
TEST_AUTH_API_PRODUCTION_BLOCK
TEST_LOGIN_GET_PRODUCTION_BLOCK
API_ROUTE_ORDER
SPA_FALLBACK_ORDER
PRODUCTION_BUILD
PRODUCTION_START
DATABASE_SCHEMA_READY
PRODUCTION_SEED_SAFETY
TEST_DATA_EXCLUSION

PASS / FIXED / FAIL

로 보고.

중요:

Production DB와 Production Browser 검증은
아직 Production Deployment가 없기 때문에
지금 PASS를 날조하지 마.

대신 코드 단계 Blocker가 모두 해결되었다면:

"첫 Production Publish를 진행해도 되는 상태이며,
배포 직후 Post-Deployment Verification이 필요함"

이라고 명확하게 보고해.
