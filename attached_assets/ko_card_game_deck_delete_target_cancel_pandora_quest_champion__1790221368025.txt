KO CARD GAME — 4 BUG BUNDLE
DECK DELETE + TARGET CANCEL + PANDORA QUEST DOUBLE PROGRESS + CHAMPION ADMIN SAVE

현재 사용자 확인 버그/요청:

1. 덱 삭제가 안 됨
2. 타겟을 지정하는 상황에서 취소할 수 있도록 취소 버튼 필요
3. 챔피언 판도라의 Quest 진행도가 한 번에 2씩 올라감
4. 관리자 페이지에서 Champion 설정 저장이 간헐적으로 실패함

목표:
네 문제를 각각 임시 우회하지 말고
UI → API → Game Action/Event → State/Persistence 흐름을 실제로 추적해서
재현 가능한 원인을 고친다.

중요:
Browser가 unavailable이어도 구현/자동 테스트를 중단하지 말 것.
IMPLEMENTATION / AUTOMATED VERIFICATION / BROWSER E2E를 분리해 보고한다.

Deck UI delete button

반드시 확인:

- 버튼 클릭 자체가 안 되는가?
- confirm 후 request가 안 나가는가?
- 잘못된 method/path인가?
- 401/403/404/409/500인가?
- API는 성공했는데 UI cache가 남는가?
- activeDeckId/selectedDeckId reference 때문에 삭제가 rollback되는가?
- 마지막 덱/기본 덱/AI Deck restriction이 있는가?
- FK constraint가 있는가?
- deck cards child rows 때문에 delete 실패하는가?
- stale React query/cache 문제인가?
- double-click race인가?

2. 덱 삭제 공식 동작
==================================================

사용자가 소유한 삭제 가능한 덱에서 삭제 확인:

→ 해당 덱 삭제
→ 덱 목록에서 즉시 제거
→ 새로고침 후에도 삭제 상태 유지

삭제 대상이 현재 selected/active deck이면:

- dangling deck id를 남기지 말 것
- 다른 사용 가능한 덱이 있으면 기존 프로젝트의 canonical fallback 정책 사용
- fallback 정책이 없다면 selected/active를 안전하게 null/none 상태로 만들고
  UI가 깨지지 않게 한다
- 임의로 다른 덱을 자동 편집하지 말 것

삭제 불가 정책이 실제로 존재하는 덱이라면:
버튼 무반응이 아니라 명확한 사용자 메시지를 보여준다.

예:
"현재 사용 중인 덱은 삭제할 수 없습니다."
같은 restriction은 실제 product rule이 존재할 때만 유지.

6. 사용자 시작 action의 Cancel semantics
==================================================

사용자가 action을 시작했지만
타겟 확정 전인 경우:

예:
Champion Ability 클릭
→ target select mode
→ 취소

결과:

- action 미사용
- Gold/비용 미소모
- ability use count 미증가
- Quest progress 미증가
- cooldown/turn-use flag 미소모
- card zone 이동 없음
- effect 미발동
- pending choice 삭제
- target highlight 제거
- 원래 플레이 가능한 상태로 복귀

즉 target confirm 전에는 canonical action commit이 일어나지 않는 구조가 이상적.

현재 구조가 먼저 commit한 뒤 target을 고르는 방식이라면
기존 transaction/snapshot/continuation 구조를 조사해서
안전하게 pre-commit 방식으로 정리한다.

ad-hoc refund 여러 군데 추가 금지.

==================================================
7. 이미 commit된 trigger의 선택 취소
==================================================

ON_ENTER 등 이미 앞 action이 commit된 뒤
후속 PLAYER_CHOICE가 뜨는 구조도 조사.

예:
카드는 이미 FIELD에 정상 진입
→ ON_ENTER PLAYER_CHOICE가 뜸

사용자가 취소할 때:

- 이미 정상 commit된 카드 play 자체를 임의 rollback하지 말 것
  (현재 engine이 atomic rollback을 공식 지원하는 경우 제외)
- pending target selection만 안전하게 종료
- 해당 optional/abortable choice effect는 no-op 처리
- stale continuation 남기지 말 것
- input lock 해제
- 다음 legal action 가능

강제 선택이 반드시 필요한 effect라면
현재 product semantics를 확인.
사용자 요청은 "타겟 지정 상황에서 취소 가능"이므로
가능하면 choice flow를 abortable로 만들되
GameState를 불완전하게 두면 안 됨.

10. BUG C — 챔피언 판도라 Quest progress가 2씩 증가
==================================================

현재 공식 Quest 의미:

"자신의 고유 능력으로 선수 카드를 5번 리타이어 시킵니다."

현재 저장 condition에는 개념적으로:

event = WRESTLER_RETIRED
cardType = WRESTLER
required = 5
sourceActionType = USE_CHAMPION_ABILITY

가 존재한다.

따라서:

판도라 Champion Ability 하나의 사용으로
선수 하나를 실제 RETIRE시키면
Quest progress는 정확히 +1.

+2 금지.

==================================================
11. Pandora double progress — root cause trace
==================================================

반드시 실제 이벤트 trace를 남긴다:

USE_CHAMPION_ABILITY action id
→ DAMAGE effect id
→ lethal HP result
→ BEFORE_RETIRE
→ WRESTLER_RETIRED event
→ Quest matcher
→ progress mutation

한 qualifying retirement마다 아래 식별값 확인:

- actionId
- effectExecutionId
- eventId
- sourceActionType
- sourceChampionId
- targetInstanceId
- questProgressBefore
- questProgressAfter

중복 증가 원인 후보를 모두 검사:

- 같은 WRESTLER_RETIRED event가 2번 emit
- RETIRE + CARD_RETIRED 둘 다 Quest가 듣고 있음
- local + server가 각각 progress 적용
- executeAction path + event listener path 두 군데에서 progress 적용
- optimistic UI + authoritative state 중복
- Quest matcher가 같은 event를 두 번 consume
- reconnect/replay가 동일 event를 재적용
- Champion Ability damage handler가 직접 progress 올리고 generic Quest도 올림
- duplicate listener registration
- React StrictMode/UI issue가 canonical state까지 중복 action dispatch
- online websocket duplicate event
- AI/local match와 online path 불일치

카드/Champion 이름으로:
`if Pandora then /2`
같은 보정 절대 금지.

==================================================
12. Quest progress idempotency
==================================================

Quest progression은 canonical event 기준 exactly once.

가능하면 unique event identity/eventId를 기준으로
같은 Quest가 동일 event를 두 번 consume하지 못하게 한다.

단순 UI dedupe가 아니라
authoritative GameState progress mutation 자체가 exactly once여야 한다.
