==================================================

따라서 먼저 아래 중 무엇인지 구분한다.

CASE C1:
사용자 요청 자체가 실제로 모호함.

CASE C2:
Provider prompt가 이미 충분히 명확한 mechanic을
불필요하게 clarification하도록 유도함.

CASE C3:
현재 DSL capability 설명이 부족해서
provider가 지원 여부를 판단하지 못함.

CASE C4:
필수 server context가 provider prompt에 누락됨.

CASE C5:
예시가 실제 C mechanic과 잘못 매칭됨.

==================================================
5. clarification이 정말 필요한 경우
==================================================

요청이 실제로 두 가지 이상 의미로 해석되어
실행 결과가 달라지는 경우에만 clarification 허용.

예:

대상
시점
범위
지속시간

이 명확하지 않아
runtime semantics를 결정할 수 없다면
clarification이 정당할 수 있다.

하지만 이미 prompt에 명시된 내용을
AI가 다시 묻는 것은 실패.

==================================================
6. 불필요한 clarification 제거
==================================================

C가 충분히 명확한 요청이라면
provider system prompt에서 다음을 점검:

- "모르면 무조건 질문" 같은 과도한 지시
- 지원 capability인데도 clarification 우선하도록 한 규칙
- 실제 C mechanic example 누락
- schema가 요구하는 field를 prompt가 설명하지 않음

수정 원칙:

"명확한 요청 + 지원 capability"
→ structured draft 생성

"실제로 모호한 요청"
→ clarification
