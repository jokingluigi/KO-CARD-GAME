KO 카드게임 Online PvP

[3단계]
LOW-COST RECONNECT + TURN TIMER + DISCONNECT RECOVERY
+ ACTIVE MATCH RESTORATION

을 구현해줘.

전제:

Stage 1에서 이미 구현된:

- Server-authoritative GameState
- OnlineMatch persistence
- Match Snapshot
- State Version
- Server Game RNG
- WebSocket
- Session authentication
- Viewer sanitization
- Action validation
- Match Result
- Surrender
- Multiple concurrent matches

Stage 2에서 이미 구현된:

- Online Battle menu
- Quick Match
- Private Room / Room Code
- Ready
- Match creation
- Low-cost ephemeral Queue/Room
- Multiple rooms / matches

를 반드시 재사용한다.

절대로 Online Engine / Matchmaking / WebSocket 시스템을
새로 중복 구현하지 마.

==================================================
0. 이번 단계 목표
==================================================

실제 유저가 Online Match 도중:

- 브라우저 새로고침
- 잠깐 인터넷 끊김
- WebSocket disconnect
- 탭 종료 후 빠른 복귀
- 서버 process restart
- 상대 AFK
- Turn timeout
- 동일 계정 여러 탭

상황을 만나도
Match가 즉시 망가지지 않게 한다.

핵심 UX:

Online Match
↓
연결 끊김
↓
GameState는 Server에 안전하게 유지
↓
재연결
↓
동일 Match 복귀
↓
최신 sanitized GameState 재수신
↓
계속 플레이

==================================================
1. 저비용 절대 원칙
==================================================

이번 단계에서도 다음 금지:

- 매초 DB write
- 매초 Turn Timer DB update
- 매초 reconnect 상태 DB write
- Match 상태 polling
- 1초마다 opponent online query
- Presence DB heartbeat
- 별도 Reconnect Server
- Redis
- Worker Server
- cron으로 active match 전체 반복 scan
- 모든 active match를 server boot 때 무조건 memory load

초기 베타는:

Replit Autoscale
Maximum Machines = 1

전제로 저비용 운영.

==================================================
2. Turn Timer는 timestamp 기반
==================================================

턴 타이머를:

90
89
88
87...

처럼 매초 Server/DB에서 감소시키지 마.

대신 Server State에:

turnStartedAt
turnDeadlineAt

또는 equivalent timestamp 저장.

예:

turnDeadlineAt = currentServerTime + configuredTurnDuration

Client는:

turnDeadlineAt - current time

으로 화면 숫자를 표시.

실제 timeout 판정은 SERVER 시간 기준.

==================================================
3. Turn Timer Config
==================================================

Turn duration을 하드코딩 여러 곳에 하지 마.

중앙 Config 사용.

예:

ONLINE_MATCH_CONFIG {
  turnTimeLimitSeconds
  reconnectGraceSeconds
  matchRestoreWindow
}

현재 실제 프로젝트 Config 스타일이 있다면 재사용.

초기값은 합리적인 기본값을 둘 수 있지만
한 곳에서 쉽게 변경 가능해야 한다.

추천 초기 베타 예시:

turnTimeLimitSeconds: 90
reconnectGraceSeconds: 60

하지만 값보다
config-driven 구조가 더 중요하다.

==================================================
4. 매초 DB 저장 금지
==================================================

Turn Timer DB persistence는:

TURN START
또는 TURN TRANSITION

시점에:

turnDeadlineAt

한 번만 저장.

다음은 절대 금지:

remainingSeconds=89 UPDATE
remainingSeconds=88 UPDATE
remainingSeconds=87 UPDATE

==================================================
5. Server Timer 실행 방식
==================================================

Active Match runtime에서는
현재 turnDeadlineAt 기준으로:

하나의 timeout

을 예약할 수 있다.

예:

setTimeout(onTurnExpired, deadline-now)

1초 interval 금지.

턴이 변경되면:

기존 timeout cleanup
새 deadline 기준 timeout 1개 생성.

==================================================
6. Turn timeout 발생
==================================================

Server deadline 도달:

현재 Match/version/turn을 다시 확인.

stale timer라면 아무것도 하지 않음.

정상 timeout이면
Server-authoritative Action으로 처리.

기본 정책:

AUTO_END_TURN

또는 프로젝트에서 정의한 timeout action.

Client가 자동으로 End Turn을 보내는 구조 금지.

Server가 처리.

==================================================
7. pendingSelection 중 timeout
==================================================

매우 중요.

PLAYER_CHOICE 상태에서
시간이 끝날 수 있다.

절대로 random target을 임의 선택하지 마.

현재 KO에서 별도 규칙이 없다면
timeout 시 해당 unresolved effect를
안전한 generic cancellation/turn resolution 정책으로 처리해야 한다.

기존 Engine에 selection timeout 정책이 있다면 재사용.

없다면:

새 카드 룰을 임의로 만들지 말고
ONLINE_SELECTION_TIMEOUT_REQUIRED로 분리하여
안전한 generic 처리 구조만 구현하고 보고.

GameState corruption은 절대 허용하지 마.

==================================================
8. Turn timeout Event
==================================================

Timeout은 Event로 기록 가능:

TURN_TIMEOUT

metadata:

matchId
playerId
turnNumber

Client Presentation에서:

"시간 초과"

정도의 짧은 안내 가능.

DB에 초마다 timer event를 저장하지 마.

==================================================
9. Client Timer는 표시 전용
==================================================

Client Timer는:

requestAnimationFrame
또는 적절한 UI timer

로 표시 가능.

하지만 Client 숫자가 0이라고
직접 END_TURN 처리 금지.

항상 Server Event를 기다려라.

MATCH_SNAPSHOT / RESYNC에서:

Client는 간단한 offset 계산을 사용해
표시 타이머를 보정.

과도한 NTP 시스템 만들지 마.

11. Disconnect 정의

Participant connection 상태:

FORFEITED

또는 equivalent.

GameState 자체와
connection state를 구분.

15. Disconnect timeout
==================================================

reconnectDeadlineAt까지 복귀하지 않으면:

여전히 disconnected 상태라면

resultReason 예:

DISCONNECT_TIMEOUT

==================================================

20. Match Resume
==================================================

재접속 시 Server가:

최신 persistent GameState
또는 현재 Active Runtime GameState

중 authoritative 최신 state를 사용.

viewer sanitization 수행.

Client에:

MATCH_RESUME_SNAPSHOT

또는 기존 MATCH_SNAPSHOT 재사용.

포함:

matchId
stateVersion
sanitized GameState
current turn
turnDeadlineAt
serverTime
connection state
pendingSelection if viewer owns it
필요한 current match metadata

==================================================
21. Presentation 재생 정책
==================================================

재접속 후
지난 30초 동안 놓친 모든 애니메이션을
처음부터 재생하려고 하지 마.

기본 원칙:

현재 authoritative snapshot으로 즉시 복구.

진행 중 Animation은 버리고
현재 GameState를 정상 화면으로 렌더.

필요하다면 최근 중요 Event 1~몇 개만
informational history로 보여줄 수 있지만
필수 아님.

==================================================

==================================================

Stage 1 viewer sanitization 반드시 적용.

재접속한다고:

hidden generated card

노출되면 FAIL.

==================================================
26. Server Restart Recovery
==================================================

중요.

Autoscale / deploy / process restart로
in-memory OnlineMatchRuntime이 사라질 수 있다.

그렇다고 ACTIVE Match DB state까지
잃으면 안 된다.

==================================================
27. Lazy Restore
==================================================

비용 절감을 위해
Server boot 때 모든 ACTIVE Match를
무조건 memory에 load하지 마.

대신:

User가 Match에 reconnect하거나
match subscription/action이 들어올 때:

runtime이 memory에 없으면
DB에서 해당 Match를 읽고
restoreOnlineMatchRuntime(matchId)

실행.

즉 Lazy Restore.

==================================================
28. Runtime Restore 내용
==================================================

복원:

serialized Match Snapshot
serialized GameState
stateVersion
status
players
turnDeadlineAt
reconnectDeadline metadata
RNG state
pendingSelection
필수 match metadata

Non-serializable UI state는 없음.

==================================================
29. RNG 복구
==================================================

매우 중요.

Server restart 후에도
deterministic RNG state가 복구되어야 한다.

재시작했다고 RNG seed/reset하면 안 된다.

그렇지 않으면 Random 결과가 달라질 수 있음.

==================================================
30. Turn Timer 복구
==================================================

Runtime restore 시:

현재 turnDeadlineAt 확인.

아직 미래:
→ 남은 시간 기준 timeout 다시 예약.

이미 지남:
→ 즉시 timeout resolution을 queue에 넣음.

단 중복 timeout 처리 방지.

==================================================
31. Disconnect Timer 복구
==================================================

reconnectDeadlineAt가 persist되는 구조라면:

restore 시 동일하게 처리.

이미 deadline 지남:
→ match state 재확인
→ 필요하면 disconnect loss 처리.

==================================================
32. Restore Lock
==================================================

두 Client가 동시에 reconnect해서:

같은 matchId restore를
동시에 두 번 실행하면 안 된다.

per-match restore lock / promise deduplication 사용.

==================================================
33. Match Runtime 하나만
==================================================

하나의 matchId에 대해
현재 Server Process 내부 Runtime은 정확히 하나.

중복 Runtime 금지.

==================================================

Tab B

둘 다 동시에 Action을 보내게 두면 안 된다.

==================================================

한 User / 한 Match에 대해

추천:

가장 최근에 정상 인증되어 Match에 연결된 connection을

이전 connection:

SESSION_REPLACED
또는
MATCH_CONTROL_MOVED

알림.

이전 connection은 더 이상 Action 전송 불가.

39. Stale Action after Reconnect
==================================================

STALE_STATE
또는 RESYNC_REQUIRED.

40. Resync
==================================================

Client가 sequence gap 또는 version mismatch를 감지하면:

전체 Page reload 대신
RESYNC 요청 가능.

latest sanitized Match Snapshot

==================================================
41. Event sequence recovery
==================================================

WebSocket Event sequence:

101
102
104

처럼 gap 발견 시:

Client가 state resync 요청.

초기 버전에서

Snapshot resync로 복구해도 됨.

==================================================
42. Opponent AFK와 Disconnect 구분
==================================================

Connection은 살아 있는데
아무 Action도 안 하는 경우:

Disconnect가 아니라 Turn Timer가 처리.

별도 AFK heartbeat DB 시스템 만들지 마.

즉:

CONNECTED + no action
→ Turn timeout

DISCONNECTED
→ reconnect grace.

==================================================
43. 반복 timeout 정책
==================================================

유저가 매 턴 계속 시간초과하는 경우
자동 패배 정책을 만들지 여부는
현재 규칙에 없으면 임의로 추가하지 마.

우선 각 턴 AUTO_END_TURN까지만.

향후 AFK strike system은 별도 기능.

==================================================
44. Reconnect와 Turn Timer 관계
==================================================

상대가 disconnect했다고
현재 Turn Timer를 자동으로 무한 정지시키지 마.

정책은 중앙 config/online rules로 분리.

초기 구현에서는
reconnect grace와 turn timer를 독립적으로 관리 가능.

단 같은 Player에 대해
turn timeout + disconnect loss가 동시에 발생하면
Match Result가 두 번 생성되지 않게.

59. Timer leak 방지
==================================================
