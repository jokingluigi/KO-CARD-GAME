KO CARD GAME — FIX ONLY:
UNEXPECTED "위리너" ENTITY + GENERAL MATCH LAG

이번 작업에서는 아래 2개만 처리한다.

1. 경기 중 정체불명의 "위리너" 카드/엔티티가 나타나는 문제
2. 경기 중 전체적으로 느려지거나 반응이 늦어지는 일반적인 게임 렉

이번 작업의 핵심은
원인을 추적한 뒤 최소 수정으로 해결하는 것이다.

"위리너"를 이름으로 하드코딩해서 숨기거나 삭제하지 마.

성능 문제도 근거 없이 전체 구조를 갈아엎지 마.

==================================================
0. FIX-FIRST
==================================================

각 항목은 반드시:

재현
→ 실제 source 추적
→ root cause
→ 최소 수정
→ regression
→ typecheck/build

순서로 진행한다.

브라우저가 없어도
코드 수정과 자동 검증은 계속한다.

==================================================
PART A — 정체불명의 "위리너" 엔티티 출현
==================================================

현재 신고:

게임 중 사용자가 의도하지 않은
"위리너"라는 카드/엔티티가 필드 또는 게임 상태에 나타나는 경우가 있다.

이 엔티티가:

- 실제 CardDefinition인지
- placeholder인지
- fallback인지
- 잘못된 Token인지
- Generate 결과인지
- Summon 결과인지
- Revive 결과인지
- Champion Token 오해석인지
- AI deck/cardPool fallback인지

먼저 정확히 추적한다.

==================================================
1. 절대 이름으로 삭제하지 마
==================================================

금지:

if (card.name === "위리너") removeCard();

금지:

UI에서 "위리너"만 숨김.

금지:

해당 이름을 placeholder blacklist에 추가해서
증상을 감춤.

반드시
왜 그 CardInstance가 생성되었는지 찾아야 한다.

==================================================
2. CardInstance lineage 추적
==================================================

"위리너"가 나타나는 순간
가능하면 다음 정보를 추적한다.

- CardInstance ID
- CardDefinition ID
- ownerId
- zone
- createdBy action/event
- source CardInstance
- source CardDefinition
- source effect ID
- creation reason
- turn number
- action sequence/event sequence

현재 engine에 debug lineage가 없다면
Development/Test에서만 사용할 수 있는
최소한의 추적 정보를 추가할 수 있다.

Production UI에 debug 정보 노출 금지.

==================================================
3. 가능한 생성 경로 전부 확인
==================================================

최소 확인:

PLAY_FROM_HAND
SUMMON
GENERATE
REVIVE
DEPLOY_CHAMPION_TOKEN
TOKEN CREATION
COPY/CLONE
fallback CardDefinition resolution
AI deck construction
match initial cardPool

legacy serialized CardInstance restore

어느 경로가 실제 원인인지 증명한다.

==================================================
4. Missing CardDefinition fallback 확인
==================================================

특히 확인:

CardDefinition ID를 찾지 못했을 때
임의의 첫 카드,
기본 카드,
placeholder 카드,
특정 이름의 카드

를 대신 사용하는 코드가 있는지.

잘못된 ID가 들어왔는데
다른 실제 카드로 조용히 대체하는 구조라면 위험하다.

가능하면:

missing definition
→ explicit validation/error handling

로 처리하고
다른 실제 CardDefinition으로 대체하지 않는다.

단 정상적인 공식 fallback mechanic이 있다면
그 규칙은 유지.

==================================================
5. Token / Champion Token 구분
==================================================

Champion Token은
authoritative Champion → linked Token relation을 사용한다.

이 문제를 고친다고
Champion Token linkage를 이름/태그 기반으로 바꾸지 마.

ordinary SUMMON of same CardDefinition과
Champion Token deployment context도 계속 구분한다.

==================================================
6. Generate / Summon target 확인
==================================================

효과가 특정 CardDefinition을 생성해야 한다면
실제 structured effect/AST가 지정한 ID와
생성된 definition ID가 동일해야 한다.

index mismatch,
array fallback,
undefined ID,
stale catalog ordering

등을 확인한다.

==================================================
7. AI deck / cardPool 확인
==================================================

AI deck 또는 cardPool 구성 과정에서

invalid card
missing definition
empty slot

을 채우기 위해
임의 카드가 삽입되는지 확인.

특히:

array[0]
firstPublishedCard
defaultCard

같은 silent fallback이 있다면 조사.

공식적으로 필요한 fallback이 아니라면
임의 카드 삽입을 막는다.

==================================================

기대:

기대:
다른 실제 카드를 임의 대체하지 않음.

현재 architecture에 맞는 안전한 reject/error path 사용.

TEST W7

AI deck/cardPool initialization.

기대:
정의되지 않은 slot 때문에
임의의 "위리너" 또는 다른 카드가 삽입되지 않음.

canonical correctness 우선.

==================================================

현재 architecture와 맞는 방식으로 최적화.

이번 작업에서 effect semantics는 변경하지 마.

==================================================
14. AI scheduler
==================================================

AI scheduler를 이미 수정한 경우
그 동작을 깨지 않는다.

확인:

- 같은 turn에 scheduler 여러 개 생성
- stale timer 계속 생존
- action 후 scheduler 중복 호출
- timeout + normal scheduler 동시 실행

이런 것이 성능 문제라면 수정 가능.

AI 의사결정 규칙 자체는 바꾸지 마.

==================================================
15. Presentation / Animation
==================================================

확인:

- 처리 완료된 presentation event가 queue에서 제거되는가
- 동일 event가 중복 enqueue되는가
- animation timer가 cleanup되는가
- 화면에서 보이지 않는 오래된 animation이 계속 살아 있는가

presentation을 없애서 성능을 개선하지 마.

정상 연출은 유지해야 한다.
