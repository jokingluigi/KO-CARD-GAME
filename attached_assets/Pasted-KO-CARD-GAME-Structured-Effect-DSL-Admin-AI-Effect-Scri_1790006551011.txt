KO CARD GAME의 현재 Structured Effect DSL과 Admin AI 효과 생성기를
"범용 Effect Script Engine + 자연어 AI Compiler" 구조로 확장해줘.

이번 작업에서 매우 중요한 추가 요구사항이 있다.

==================================================
최우선 비용 / AI 호출 규칙
==================================================

OpenAI API는 오직 Admin에서 사용자가 명시적으로:

- AI 효과 생성
- AI 효과 재생성
- clarification 답변 후 다시 생성

같은 버튼을 눌렀을 때만 호출한다.

게임 Runtime에서는 OpenAI API를 절대 호출하지 않는다.

즉 다음에서는 OpenAI 호출 횟수가 반드시 0이어야 한다.

- 실제 카드 효과 발동
- AI Match
- Online PvP
- Quick Match
- Friendly Match
- 카드 공격
- 카드 소환
- 피해/회복
- targeting
- PLAYER_CHOICE
- turn start/end
- quest 진행
- Champion ability
- Effect Script validation
- Effect Script 저장
- Admin 페이지 단순 로딩
- 저장된 효과 preview
- reconnect/resync
- game state serialization
- effect interpreter
- server startup

저장된 Effect Script는 순수 JSON 데이터이고,
실제 게임에서는 KO 서버의 Script Interpreter가 직접 실행한다.

절대:

카드 효과 발동
→ OpenAI
→ 결과 결정

구조로 만들지 마.

정확한 구조는:

Admin에서 자연어 작성
→ OpenAI API 1회
→ Effect Script JSON 생성
→ server validation
→ form에 적용
→ Admin 저장

이후:

게임 플레이
→ 저장된 Effect Script JSON 읽기
→ KO Script Interpreter가 실행
→ Action / Event / GameState 처리

이며 이 Runtime 과정의 OpenAI API 비용은 0이어야 한다.

==================================================
AI 비용 폭주 방지
==================================================

한 번의 사용자가 누른 [AI 효과 생성] 요청에
provider 호출은 기본적으로 정확히 1회만 허용한다.

자동 재시도 루프를 만들지 마.

provider 오류나 invalid output이면:

- 자동으로 5번, 10번 재생성 금지
- 서버가 알아서 계속 AI 호출 금지

오류를 Admin에게 반환하고
사용자가 직접 다시 생성 버튼을 눌렀을 때만 새 호출을 허용한다.

네트워크 SDK 자체의 기본 retry가 존재한다면
현재 provider SDK 설정을 조사하고,
비용 폭주 가능성이 있는 반복 retry는 제한한다.

AI에게 매 요청마다 다음을 보내지 마:

- repo 전체 source
- 전체 game engine 코드
- 전체 Production DB
- 모든 카드의 전체 상세 데이터
- 전체 event history

대신 최소 context만 사용한다.

최소 context 예:

- Effect Script schema의 compact representation
- 지원 trigger 목록
- 지원 selector/filter/action/value 목록
- 선택 중인 카드/Champion context
- 해당 요청에 실제로 필요한 CardDefinition 후보
- 사용자의 자연어 효과 설명

CardDefinition 후보가 필요하면
전체 카드 데이터를 무조건 prompt에 넣지 말고
서버에서 먼저 검색/필터링해서 필요한 후보만 전달한다.

AI output도 JSON Effect Script만 반환하게 하며
불필요한 긴 설명문 생성을 금지한다.

현재 provider에서 output token limit 설정이 가능하면
Effect Script 작성에 충분한 합리적인 상한을 둔다.

현재 사용 중인 AI model을 임의로
더 비싼 model로 변경하지 마.

model이 configurable하다면 기존 환경변수/설정을 유지하거나
필요 시 별도 EFFECT_AI_MODEL 설정으로 분리하되
기존보다 고비용 모델을 자동 선택하지 마.

==================================================
최종 목표
==================================================

현재 Admin AI 효과 생성기는
기존 엔진에 이미 존재하는 action 조합만 만들 수 있다.

이 방식은 새로운 카드 효과를 만들 때마다
TypeScript engine action을 추가해야 해서 자동 AI 기능의 가치가 낮다.

목표는:

자연어 카드 효과
→ AI가 범용 Effect Script 생성
→ 서버가 schema / semantic validation
→ Admin form에 자동 적용
→ 사용자가 저장
→ 실제 게임 엔진이 Script 실행
→ AI Match / Online PvP에서 실제 효과 발동

이다.

카드마다 TypeScript 코드를 새로 작성하지 않는다.

==================================================
목표로 하는 카드 효과 표현력
==================================================

최소 다음 정도의 효과는
새 카드 전용 TypeScript 코딩 없이 Script만으로 표현 가능해야 한다.

예시 A

"등장: 적 챔피언에게 2 피해를 준다."

예시 B

"이 카드가 죽으면 내 무덤의 좀비 수만큼 내 챔피언을 회복한다."

예시 C

"공격할 때 상대 손에서 비용이 가장 높은 카드의 비용을 2 증가시킨다."

예시 D

"상대 덱 위 3장 중 비용이 가장 높은 선수를 내 손에 복사한다."

예시 E

"이번 턴에 죽은 선수들의 공격력 합만큼 상대 챔피언에게 피해를 준다."

예시 F

"이 카드 양옆의 빈 슬롯에 각각 무작위 선수 하나를 소환하고,
그렇게 소환된 선수들에게 도발을 부여한다."

예시 G

"내 무덤에서 비용 3 이하 선수 하나를 무작위로 부활시킨다."

예시 H

"다음에 내가 사용하는 Technique의 비용을 0으로 만든다."

예시 I

"내 필드에 좀비가 3명 이상이면 이 카드는 +3/+3을 얻는다."

예시 J

"이 카드가 피해를 받을 때마다 공격력이 1 증가한다."

이런 일반적인 카드게임 gameplay effect 대부분을
데이터 Script 조합으로 표현하는 것이 목표다.

==================================================

==================================================
9. Result Reference
==================================================

이전 step의 실제 결과를
후속 step이 참조할 수 있게 한다.

예:

step id = "summonFriends"

SUMMON 2 cards

↓

ADD_KEYWORD
target = result("summonFriends")

이때 실제 성공적으로 소환된 CardInstance만 result에 포함한다.

다른 resolution의 결과와 섞이면 안 된다.

기존:

SAME_TARGET
LAST_DESTROYED_TARGETS

등을 범용 result frame으로 정리할 수 있다면
backward compatibility를 유지하며 일반화한다.

==================================================
10. Resolution Local State
==================================================

Script 실행 중 필요한 임시 result/variable은
resolution frame 안에 유지한다.

GameState에 불필요하게 영구 저장하지 않는다.

PLAYER_CHOICE 때문에 실행이 중단되는 경우에만
필요한 continuation state를 serializable하게 저장한다.

resolution 종료 시 cleanup.

==================================================
11. Random
==================================================

모든 random은 기존 deterministic RNG만 사용한다.

Math.random() 금지.

Online PvP에서는 서버만 random 결과를 결정한다.

클라이언트는 canonical random result를 결정하지 않는다.

Random selector가 최소 다음에서 동작 가능하도록 한다.

- cardPool
- hand
- deck
- board
- graveyard

hidden information은 서버에서만 처리.

==================================================
12. Zone 이동 / Copy
==================================================

가능한 경우 generic operation을 구축하되
기존 canonical game functions를 재사용한다.

HAND → BOARD
DECK → HAND
GRAVEYARD → HAND
GRAVEYARD → BOARD
BOARD → HAND
→ REMOVED_FROM_GAME

단:

PLAY_FROM_HAND
SUMMON
REVIVE
Champion Token deployment

의 semantics를 섞지 않는다.

COPY는 원본 CardInstance를 훔치는 것과
CardDefinition 기반 generated copy를 만드는 것을 구분한다.

==================================================
13. Cost modification
==================================================

최소 다음 패턴을 표현 가능하게 한다.

cost +N
cost -N
cost = 0

지원되는 기존 duration이 있다면:

THIS_TURN
UNTIL_PLAYED
PERMANENT

등을 현재 규칙에 맞게 사용.

없는 duration을 있는 것처럼 만들지 않는다.

generated/token card는 0G 허용.

비용 floor:

Math.max(0, ...)

규칙 유지.

18. Action → Event → GameState
==================================================

가능한 한 기존 canonical engine function을 호출한다.

Effect Script
→ Engine Operation
→ GameEvent
→ GameState

구조 유지.

source attribution도 유지.

22. Online PvP
==================================================

클라이언트는:

- 렌더링
- target 선택
- action 제출

역할만 한다.

OpenAI API 호출 금지.

특히 Online match 중:

OPENAI_API_KEY 사용 0회
provider function 호출 0회
/admin/effects/generate 호출 0회

여야 한다.

- public cardPool 유지

- opponent hand/deck hidden
- hidden draw/generated identity redaction

==================================================
23. AI Match
==================================================

AI Match도 동일 Effect Script Interpreter를 사용한다.

AI Match의 "AI"는 게임 상대 로직이지
OpenAI API가 아니다.

AI Match 중 OpenAI API 호출은 반드시 0회다.

==================================================
24. Legacy 효과 호환
==================================================

Production 기존 카드 데이터를 자동 migration하지 않는다.

기존 Structured Effect DSL은 계속 동작해야 한다.

가능하면 기존 Structured effect를
공용 internal execution representation으로 normalize하거나
legacy/new Script 둘 다 지원한다.

DB migration이 필요하다면 자동 실행하지 말고 보고한다.

==================================================
25. Admin AI Compiler
==================================================

현재:

POST /api/admin/effects/generate

를 자연어 → Effect Script compiler endpoint로 사용한다.

이 endpoint만 OpenAI provider를 호출할 수 있다.

provider call site를 가능한 한 한 module로 집중시킨다.

게임 engine package가 OpenAI SDK를 import하면 안 된다.

game runtime package가 OPENAI_API_KEY를 읽으면 안 된다.

==================================================
26. Admin AI 호출 횟수 제한
==================================================

사용자가 [AI 효과 생성] 한 번 클릭:

→ 최대 provider request 1회

기본 규칙.

invalid script이면
OpenAI에게 자동으로 다시 물어보지 않는다.

Admin에게 validation error를 보여준다.

사용자가 직접 [다시 생성]을 눌러야
두 번째 provider 호출이 발생한다.

Clarification도:

AI가 NEEDS_CLARIFICATION 반환
→ 질문 표시
→ 사용자가 답 입력
→ 사용자가 다시 생성 실행
→ 그때 새 API 1회

구조.

==================================================
27. Prompt 크기 최소화
==================================================

매 요청마다 repo 소스 전체를 보내지 않는다.

Effect Script schema도
필요한 concise representation을 사용한다.

Card catalog를 전부 prompt에 넣지 않는다.

CardDefinition 이름 resolution은 가능한 한 서버에서 한다.

예:

사용자:
"좀비를 소환"

서버:
관련 CardDefinition candidate 검색

→ 그 후보만 AI context에 제공

AI가 모든 카드 DB를 받을 필요가 없게 한다.
