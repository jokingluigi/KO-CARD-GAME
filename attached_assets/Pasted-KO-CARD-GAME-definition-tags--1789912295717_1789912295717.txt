KO CARD GAME에 중요한 신규 카드 메타데이터 시스템을 추가해줘.

목표:
모든 카드 definition에 "태그(tags)" 정보를 추가한다.

태그는 종족/소속/분류와 비슷한 카드 고유 속성이다.

예:
["용병"]
["용병", "인간"]
["악마", "언데드", "마족"]

한 카드가 가질 수 있는 태그는 최대 3개.

이번 작업은 카드 데이터 구조, API, 관리자 페이지, 게임 엔진에서
공통으로 사용할 수 있는 canonical tag 시스템을 만드는 작업이다.

==================================================
1. DB schema
==================================================

cards 테이블에 다음 필드를 추가:

tags

권장 타입:
PostgreSQL text[]

조건:
- NOT NULL
- 기본값 빈 배열 []
- 최대 3개
- 중복 금지
- 빈 문자열 금지
- 앞뒤 공백 제거

기존 카드들은 migration 후 모두:

tags = []

로 안전하게 유지.

Champion 테이블에는 이번 작업에서 추가하지 않는다.
카드 cards 테이블에만 적용.

Drizzle schema와 migration을 모두 작성.

중요:
Production Supabase를 이번 단계에서 직접 수정하지 말 것.
Production 적용용 migration SQL 또는 안전한 migration 방법만 준비.

==================================================
2. API / validation
==================================================

카드 생성/수정/조회 API에 tags 추가.

응답 예:

{
  "name": "예거",
  "cardType": "WRESTLER",
  "tags": ["용병", "인간"]
}

validation:

- 배열만 허용
- 0~3개
- 각 값 trim
- 빈 문자열 거부
- 동일 태그 중복 거부
- 저장 순서는 관리자 입력 순서 유지

기존 tags 필드가 없는 오래된 데이터는
[]로 처리해서 frontend/game engine이 깨지지 않게 한다.

공유 Zod/API 타입도 함께 수정.

==================================================
3. 관리자 /admin
==================================================

카드 편집 화면에 "태그" 입력 UI 추가.

요구사항:

- 최대 3개
- 태그를 chip/badge 형태로 보여줌
- Enter 또는 추가 버튼으로 태그 추가 가능
- 각 태그 오른쪽 X로 삭제 가능
- 3개가 차면 추가 입력 비활성화
- 같은 태그 중복 추가 방지
- 공백만 있는 태그 금지

표시 예:

태그
[ 용병 × ] [ 인간 × ] [ + 태그 추가 ]

저장하면 기존 카드 정보와 함께 tags가 저장되어야 한다.

기존 카드 편집 기능:
- 이름
- 비용
- 공격력
- 체력
- 효과
- 이미지
- rarity
- cardType
등을 깨뜨리지 말 것.

==================================================
4. 카드 표시 UI
==================================================

Card Detail 등 카드 정보를 자세히 보여주는 화면에서는
태그가 존재하면 작은 badge로 표시한다.

예:

용병 · 인간

또는 badge:

[용병] [인간]

태그가 []이면 태그 영역 자체를 표시하지 않는다.

인게임 카드 본체에 무조건 크게 표시하지 말 것.
현재 카드 디자인을 망가뜨리지 않도록
우선 상세 정보 화면 중심으로 적용.

==================================================
5. 기존 "태그" 게임 메커니즘과 연결
==================================================

KO CARD GAME에는 이미 "태그"라는 효과 키워드가 존재한다.

앞으로 "같은 태그" 판정은 반드시
cards.tags 데이터를 canonical source로 사용한다.

두 WRESTLER가 같은 태그를 가진다는 뜻:

두 카드의 tags 배열에
하나 이상의 동일 문자열이 존재한다.

예:

A.tags = ["용병", "인간"]
B.tags = ["용병", "기계"]

→ 공통 "용병"이 있으므로 같은 태그 = true

A.tags = ["용병"]
B.tags = ["악마"]

→ false

공통 helper를 만들어라.

예:

sharesCardTag(cardA, cardB): boolean

또는 현재 architecture에 맞는 generic helper.

카드 이름 하드코딩 금지.

==================================================
6. 태그 키워드 규칙
==================================================

기존 공식 규칙 유지:

태그 효과는
"이번 턴에 먼저 손에서 정상적으로 플레이된 다른 아군 WRESTLER가
현재 카드와 하나 이상의 공통 태그를 가지고 있는 경우"

에 조건 만족.

반드시 PLAY_FROM_HAND만 인정.

다음은 태그 조건을 만족시키면 안 됨:

- SUMMON
- effect로 생성된 카드가 바로 SUMMON
- REVIVE
- Champion Token deploy

단,
effect로 생성된 WRESTLER라도
나중에 손에서 정상적으로 PLAY_FROM_HAND되었다면
그때는 일반 카드처럼 태그 판정 가능.

현재 턴이 끝나면 이전 PLAY_FROM_HAND 기록은 초기화되어야 함.

==================================================
7. 공통 Event/GameState 판정
==================================================

가능하면 기존 Action/Event 시스템을 사용.

태그 판정을 위해 카드 이름이나 UI 상태를 읽지 말 것.

GameState/Event에서:

PLAY_WRESTLER
entryCause = PLAY_FROM_HAND

인 실제 아군 카드의 definition.tags를 기준으로 판정.

태그 조건을 검사하는 generic condition을 만들거나
기존 condition DSL에 맞게 확장.

예:

condition:
SHARES_TAG_WITH_PREVIOUSLY_PLAYED_ALLY_THIS_TURN

이름은 현재 architecture와 맞게 정리해도 됨.

특정 카드 이름 하드코딩 금지.

==================================================
8. 테스트
==================================================

반드시 테스트:

DB/API:
- tags 없음 → []
- 1개 저장
- 3개 저장
- 4개 거부
- 중복 거부
- 빈 문자열 거부
- trim 정상 처리

공통 helper:
["용병","인간"] + ["용병"] → true
["용병"] + ["악마"] → false
[] + ["용병"] → false

게임:
1.
A tags=["용병"]
A PLAY_FROM_HAND
B tags=["용병"]
B PLAY_FROM_HAND
→ B의 태그 조건 true

2.
A tags=["용병"]
A PLAY_FROM_HAND
B tags=["악마"]
→ false

3.
A tags=["용병"]
A SUMMON
B tags=["용병"] PLAY_FROM_HAND
→ A 때문에 태그 조건이 활성화되면 안 됨

4.
A tags=["용병"] PLAY_FROM_HAND
턴 종료
다음 턴 B tags=["용병"] PLAY_FROM_HAND
→ 이전 턴 A 때문에 활성화되면 안 됨

5.
A tags=["용병","인간"] PLAY_FROM_HAND
B tags=["인간","악마"] PLAY_FROM_HAND
→ 공통 인간 때문에 true

6.
자기 자신만 존재
→ 자기 자신을 이전 태그 카드로 판정하면 안 됨

==================================================
9. 기존 데이터 안전성
==================================================

기존 49개 published 카드에 태그가 없어도
모두 정상적으로 로드/플레이되어야 한다.

migration 때문에:

- 카드 효과
- Deck
- Collection
- AI match
- admin
- card renderer

가 깨지지 않게 한다.

Production DB/Supabase는 이번 단계에서 수정하지 말 것.
