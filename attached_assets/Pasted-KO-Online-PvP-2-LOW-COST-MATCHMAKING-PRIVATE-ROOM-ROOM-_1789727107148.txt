KO 카드게임 Online PvP

[2단계]
LOW-COST MATCHMAKING + PRIVATE ROOM / ROOM CODE

를 구현해줘.

전제:

Online PvP Stage 1에서 이미 구현된:

- Server authoritative GameState
- OnlineMatch
- WebSocket
- authenticated user connection
- Match subscription
- Action validation
- viewer sanitization
- Match Snapshot
- Match persistence
- per-match runtime
- deterministic server RNG

를 반드시 재사용한다.

절대로 Online Match Engine을 새로 만들지 마.

==================================================
1. 매우 중요: 저비용 원칙
==================================================

초기 Discord 베타 규모를 전제로 한다.

다음 금지:

- 별도 Matchmaking Server
- Redis
- Message Queue
- 별도 Lobby Server
- 별도 Presence Server
- matchmaking DB polling
- 1초마다 waiting user 조회
- 1초마다 room state DB update
- waiting room heartbeat DB write
- queue 상태 DB 지속 저장
- room timer DB 지속 저장

현재 KO API/WebSocket Server 안에서 구현.

==================================================
2. 대기열과 친선방은 Ephemeral
==================================================

게임 시작 전 상태:

Quick Match Queue
Private Room Waiting State

는 초기 베타에서
Server Memory에 두어도 된다.

예:

MatchmakingQueue

PrivateRoomRegistry

중요:

Server가 재시작되어
대기열/대기방이 사라지면:

사용자에게
"대기방 연결이 종료되었습니다. 다시 시도해주세요."

정도로 안내하면 된다.

아직 시작하지 않은 방까지
DB에 영구 보존할 필요 없다.

==================================================
3. 실제 게임 시작 후에는 Persistent OnlineMatch
==================================================

두 User가 실제 게임 시작 조건을 만족하면:

Stage 1의 기존 OnlineMatch 생성 로직을 사용.

그 순간부터:

GameState
Snapshot
State Version
Result

등은 기존 Stage 1 persistence 사용.

즉:

WAITING QUEUE / ROOM
→ cheap memory state

ACTIVE MATCH
→ existing persistent OnlineMatch

구조.

여러 개 동시에 존재 가능.

9. Matchmaking Queue 구조
==================================================

초기 버전에서는 복잡한 MMR 없음.

Generic FIFO Queue로 충분.

Queue entry 최소 정보:

userId
connectionId
selectedDeckId
joinedAt

필요 이상의 정보를 저장하지 마.

Card collection 전체
Deck 전체 snapshot
GameState

등을 Queue에 넣지 마.

실제 Match 생성 시 Server가 조회/검증.

==================================================
10. 같은 User 중복 Queue 참가 금지
==================================================

한 User가:

빠른 대전 대기열에 두 번 참가하거나

브라우저 더블 클릭 때문에
QUEUE_JOIN 요청을 여러 번 보내도

Queue Entry는 하나만 존재.

idempotent하게 처리.

기존 Match 상태 확인.

응답:

13. Quick Match Pairing

==================================================

==================================================
15. Pairing 중 Deck invalid
==================================================

Queue 참가 후
Deck이 수정되어 invalid가 됐을 수 있다.

실제 Match 생성 직전에
Server가 다시 Deck 검증.

Invalid된 User는 Queue에서 제거.

해당 User:

"선택한 덱이 더 이상 유효하지 않습니다."

다른 정상 User는
다시 Queue로 복귀시키거나
계속 검색 상태 유지.

==================================================

54. Matchmaking Race Condition
==================================================

A/B/C가 거의 동시에 Queue 참가해도:

한 User가 두 Match에 들어가지 않아야 함.

Pairing 작업을 atomic하게 처리.

==================================================
55. Queue Cancel Race
==================================================

A가 취소 버튼을 누르는 순간
B와 Match가 발견될 수 있다.

둘 중 하나의 결과만 확정.

예:

Cancel 먼저 확정:
A Queue 제거, Match 생성 X.

Match Found 먼저 확정:
Cancel은 TOO_LATE/ALREADY_MATCHED.
