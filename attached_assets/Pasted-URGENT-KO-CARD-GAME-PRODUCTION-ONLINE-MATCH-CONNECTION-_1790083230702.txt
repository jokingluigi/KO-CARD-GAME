현재 다른 작업은 즉시 중단한다.

특히 다음 작업은 이번 범위에서 하지 마:

- AI Mechanic Compiler
- SCRIPT_V1
- Event History
- Admin AI
- 카드 효과
- 신규 기능
- UI redesign

현재 최우선 문제:

Replit development에서는 Online Match가 정상 연결되는데,
Render Production에서는 다시 "연결 오류"가 발생한다.

Production:

Frontend:
https://ko-card-game-vr69.onrender.com/

Node API / WebSocket:
https://ko-card-game.onrender.com/

이 Production Online Match 연결 문제를
실제 root cause까지 찾아 수정해라.

==================================================

==================================================

실행:

git status
git branch --show-current

git rev-parse origin/main
git log --oneline --decorate -15

이전 여러 작업에서도:

으로 실패했다.

따라서 Replit Preview가 local HEAD를 실행하는 반면,
Render는 오래된 GitHub origin/main을 배포하고 있을 가능성을
반드시 먼저 확인한다.

보고:

LOCAL_HEAD=
ORIGIN_MAIN=
AHEAD_BY=
SAME_CODE=YES/NO

LOCAL_HEAD != origin/main 이라면
이 사실을 Production/Replit 차이의 핵심 후보로 취급한다.

==================================================
3. Render Static Rewrite 확인
==================================================

Production frontend는 Render Static Site다.

반드시 /api/* rewrite가 Node API로 먼저 전달되고,
SPA catch-all이 그 뒤에 있어야 한다.

잘못된 예:

/* → /index.html
/api/* → Node

이 순서 때문에 /api 요청이 index.html을 반환하면 안 된다.

기대 개념:

/api/* → Node service
/* → /index.html

실제 Render 설정 / rewrite config / source config를 확인.

Online API request가 JSON 대신:

<!doctype html>

또는 frontend index.html을 받는다면
rewrite ordering 문제를 수정한다.

==================================================
4. HTTP API 자체 검사
==================================================

Node root "/"가 404인 것만으로 장애 판정하지 마.

실제 앱에서 사용하는 API route를 확인하고 테스트.

예:

auth/session
online queue
match creation
WS ticket

등 실제 존재하는 route.

Production frontend가 사용하는 endpoint와
Node server route가 일치하는지 확인한다.

다음을 구분:

404 = route/rewrite mismatch
401 = auth/session 문제
403 = origin/permission 문제
500 = backend exception
502/503 = Render service 문제

==================================================
5. WebSocket Ticket 경로 확인
==================================================

현재 Online architecture에서
WebSocket은 one-time WS ticket을 사용하는 경로가 존재한다.

Online 진입 시:

authenticated HTTP
→ WS ticket 발급
→ WebSocket connect
→ ticket consume
→ match/session attach

전체를 추적한다.

확인:

1. WS ticket 요청이 성공하는가
2. ticket response가 frontend에 정상 전달되는가
3. ticket이 undefined/null이 아닌가
4. ticket URL encoding 정상인가
5. ticket을 두 번 소비하지 않는가
6. reconnect가 이미 소비된 ticket을 재사용하지 않는가

==================================================
6. WebSocket URL 확인
==================================================

Production HTTPS 페이지에서는
WebSocket은 반드시 secure connection을 사용.

https:
→ wss:

Production에서:

ws://

사용 금지.

실제 생성되는 WebSocket URL을 확인.

정상 예 개념:

wss://ko-card-game.onrender.com/...

잘못된 예:

ws://ko-card-game.onrender.com/...
ws://localhost...
wss://Replit-host...
undefined/...

실제 runtime URL을 로그로 확인하되
ticket/token 전체 값은 로그에 출력하지 마.

==================================================
7. Frontend API URL과 WS URL을 혼동하지 마
==================================================

HTTP API는 static frontend의 relative:

/api/...

를 사용할 수 있다.

WebSocket은 Render Static rewrite가 일반 WS proxy를
담당하지 않는 구조라면
Node WebSocket host로 직접 연결해야 한다.

현재 기존 architecture를 확인한 뒤
정상 경로를 유지한다.

무조건 HTTP와 WS URL을 하나로 합치지 마.
