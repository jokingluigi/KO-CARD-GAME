KO CARD GAME의 Replit 개발환경이 현재 실제 Production KO와 **동일한 PostgreSQL Database를 사용하도록 연결을 통일해주세요.**

현재 실제 Production 사이트:

https://ko-card-game-vr69.onrender.com/

현재 확인된 구조:

* KO frontend와 관리자 사이트는 API Server를 통해 PostgreSQL을 사용함
* DB 연결은 `DATABASE_URL` 환경변수로 결정됨
* 카드와 Champion의 Source of Truth는 PostgreSQL의 `cards`, `champions` table
* Replit 개발환경과 Production 환경의 `DATABASE_URL`이 서로 다를 가능성이 있어서 데이터 불일치가 발생하고 있음
* 앞으로 Replit은 전용 테스트 계정으로만 사용할 예정임
* 따라서 Replit KO와 Production KO가 같은 DB를 사용하도록 통일하고 싶음

## 이번 작업의 목표

**Replit 개발환경의 `DATABASE_URL`을 실제 Production KO가 사용하는 PostgreSQL의 `DATABASE_URL`과 동일하게 맞춰주세요.**

완료 후에는 아래 세 환경이 같은 DB를 보게 되어야 합니다.

```text
KO 관리자 사이트 ─┐
Production KO ────┼→ 같은 Production PostgreSQL
Replit KO ────────┘
```

이렇게 되면 KO 관리자 사이트에서 카드나 Champion을 수정했을 때 별도의 sync 명령 없이 Replit KO에서도 즉시 같은 데이터가 보여야 합니다.

---

## 가장 중요한 원칙

이번 작업은 **DB 연결 통일만** 합니다.

코드 구조를 변경하거나 별도의 동기화 기능을 만들지 마세요.

다음과 같은 기능도 만들 필요 없습니다.

* `sync:prod-data`
* Production → Replit 데이터 복사 스크립트
* 별도 DB
* 별도 API
* 새로운 데이터 동기화 시스템

같은 DB를 직접 사용하게 만드는 것이 이번 작업의 목적입니다.

---

## 진행 방법

### 1. Production의 DATABASE_URL 확인

실제 Production KO가 사용하는 `DATABASE_URL`을 안전한 방식으로 확인해주세요.

가능하면 기존 Render/Production deployment 설정 또는 현재 프로젝트에 연결된 Production 환경설정에서 확인해주세요.

Secret 전체 값을 채팅이나 작업 결과에 출력하지 마세요.

화면에 보여줄 필요도 없습니다.

Production `DATABASE_URL`을 확인할 수 있다면 그 값을 그대로 Replit 개발환경의 `DATABASE_URL` Secret에 설정해주세요.

### 2. 확인할 수 없는 경우

Production의 실제 `DATABASE_URL`을 현재 Replit Agent가 접근할 수 없다면:

* 임의의 DB를 추측하지 말 것
* 새로운 DB를 만들지 말 것
* 현재 Replit DB를 Production으로 착각하지 말 것
* Supabase URL을 임의로 `DATABASE_URL`로 사용하지 말 것

이 경우에는 작업을 중단하고 **사용자가 어디에서 어떤 값만 복사하면 되는지 정확히 한 단계로 알려주세요.**

예:

> Render의 KO API Server → Environment → `DATABASE_URL` 값을 복사해서 Replit Secrets의 `DATABASE_URL`에 넣어주세요.

필요한 정보가 이것뿐이라면 다른 조사나 코드 분석은 하지 마세요.

---

## DATABASE_URL을 설정할 수 있는 경우

Replit의 `DATABASE_URL` Secret만 Production과 동일하게 변경해주세요.

다른 Secret은 변경하지 마세요.

특히 다음은 이번 작업에서 건드리지 마세요.

* `SUPABASE_URL`
* `SUPABASE_SECRET_KEY`
* `SUPABASE_STORAGE_BUCKET`
* `SESSION_SECRET`
* `ADMIN_USERNAME`
* `ADMIN_PASSWORD`
* `PORT`
* `BASE_PATH`

Production과 Replit에서 DB 연결에 실제로 `DATABASE_URL` 하나만 필요하다면 그것만 변경해주세요.

* DB reset
* DB wipe
* DB 초기화
* seed 실행
* migration 자동 실행
* schema push
* table 생성/삭제
* table truncate
* 대량 DELETE
* 대량 UPDATE
* 카드 데이터 수정
* Champion 데이터 수정
* 사용자 데이터 수정
* 관리자 데이터 수정

`npm run db:reset`, `db:push`, `seed` 등 DB 내용을 변경할 가능성이 있는 명령도 이번 작업에서는 실행하지 마세요.

**이번에는 연결만 바꾸고 읽기 테스트만 합니다.**

## 코드 수정 금지

가능하면 코드 파일은 하나도 수정하지 마세요.

현재 프로젝트가 이미 `DATABASE_URL`을 사용하는 구조이므로 환경변수만 맞추면 됩니다.

불필요한:

* 리팩터링
* API 수정
* frontend 수정
* backend 수정
* DB client 수정
* schema 수정
* package.json 수정

을 하지 마세요.

## 연결 후 검증

Replit API Server를 필요한 경우 재시작한 뒤 **읽기 전용 요청만** 사용해서 확인해주세요.

다음 API를 GET으로 확인합니다.

* `/api/cards`
* `/api/champions`

그리고 Production의 동일 API와 몇 개 항목을 비교해주세요.

비교 항목:

* `id`
* `name`
* `description`
* `status`
* 카드 효과 또는 Champion `ability_effects`

두 환경에서 동일한 데이터가 보이면 성공입니다.

Production이나 Replit에 POST / PUT / PATCH / DELETE 요청은 보내지 마세요.

---

## 관리자 데이터 실시간 반영 확인

가능하면 기존 데이터를 수정하지 않고 확인 가능한 범위에서,

Replit과 Production이 실제로 같은 PostgreSQL 연결을 사용하는지 connection 정보 또는 동일 record 조회 결과로 검증해주세요.

DB host, username, password 등 Secret 값은 출력하지 마세요.

결과는 단순히:

* 같은 DB 확인됨
  또는
* 같은 DB 여부 확인 불가

정도로만 알려주세요.

---

## Git 관련

이번 작업이 Secret/환경변수 변경만으로 끝났다면 **git commit 또는 git push는 필요 없습니다.**

Secret 값은 절대 Git repository에 저장하거나 `.env` 파일에 커밋하지 마세요.

코드 수정이 발생하지 않았다면 Git에는 아무 변경도 남기지 않는 것이 정상입니다.
