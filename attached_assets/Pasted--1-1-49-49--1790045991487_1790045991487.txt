보고서 확인했다. 이번 결과는 1차 검증으로 취급하고, 다음 미완료 범위를 이어서 진행해라. 기존 조사와 테스트를 활용하고 처음부터 다시 탐색하지 마.

## 1. 49/49 통과의 의미 정리

카드별 결과를 다음 항목으로 분리해라.

* catalog 정의 존재 여부
* 실제 Action → Event → GameState 실행 여부
* 규칙에 따른 대상·수치·횟수·타이밍 검증 여부
* 경계 조건과 관련 상호작용 검증 여부

실행에 성공했지만 기대 결과를 검증하지 못한 항목은 효과 정상 판정에서 제외하고 UNVERIFIED로 유지해라.

공식 규칙이나 승인된 카드 정의에서 기대 결과를 도출할 수 있는 항목은 assertion을 추가해서 재검증해라. 현재 구현 결과를 그대로 기대값으로 사용하지 마.

근거가 없거나 충돌하는 항목만 구체적인 질문으로 남기고 나머지는 계속 진행해라.

## 2. 개발 catalog 보정의 근거와 실제 적용 경로 확인

오심정정·저지먼트·발단의 변경에 대해 다음을 기록해라.

* 변경한 파일 또는 데이터 위치
* 변경 전후 값
* 올바른 정의라고 판단한 규칙·이력 등 근거
* 테스트 fixture 전용인지, 개발 런타임 데이터인지, 실제 제품이 사용하는 소스인지
* 기존 잘못된 값이 재시작·재생성 시 다시 생길 가능성

특히 DISABLED → PUBLISHED는 공개 상태 변경이므로 원래 비활성화 의도가 있었는지 확인해라. ENTER_FIELD → ACTIVE와 발단 효과 복구도 승인된 정의에 근거했는지 확인해라.

근거가 불명확한 변경을 확정된 버그 수정으로 처리하지 마. 그렇다고 기존 사용자 변경까지 임의로 되돌리지도 마.

Production 데이터는 수정하지 않는다. 개발 catalog 보정만으로 운영 사이트 문제가 해결됐다고 보고하지 않는다.

## 3. 자동 매치 범위 확대

기존 deterministic full-match 테스트를 활용해 전체 실행을 최소 100회까지 확대해라.

* 서로 다른 seed와 다양한 유효 덱
* 선공·후공
* 가능한 챔피언과 주요 효과 유형
* 실제 AI 및 실제 행동 처리 경로
* 행동 후 상태 불변 조건 검사
* 시간·행동 수 상한과 교착 탐지

같은 2개 시나리오를 단순 반복하고 다양한 매치를 검사했다고 보고하지 마.

실행·성공·실패·시간 초과·중단 수와 사용한 덱·seed 범위를 기록한다. 실패하면 재현 사례를 저장하고 원인 수정 후 다시 검사한다.

자동 매치에 등장하지 않거나 발동하지 않은 효과는 결정적 개별 테스트로 보완한다.

## 4. Luna fixture 검증

silence 결과를 확인할 수 있도록 대상을 생존시킨 fixture 변경은 유지할 수 있다. 다만 다음을 확인해라.

* 생존 대상의 silence 적용 결과를 실제로 assertion하는가?
* 원래 즉시 사망하는 조건에도 별도의 처리 오류가 없는가?

fixture 변경만으로 실제 구현 오류가 가려지지 않도록 두 조건을 구분해서 검사해라.

## 5. 밀크 메이드 누락 조사

관련 catalog 소스, seed, migration, 기존 정의와 이력에서 해당 카드의 존재 여부를 좁혀 조사해라.

이름 변경, 미출시, 데이터 누락, 로딩 누락 중 무엇인지 근거가 있으면 분류한다. 임의로 카드 정의를 만들거나 Production 데이터를 추가하지 마.

찾을 수 없으면 확인한 범위와 필요한 원본 정보를 기록하고 다른 작업을 계속해라.

## 6. 기존 요청의 나머지 범위 확인

카드 테스트 외에 다음 항목이 실제로 검증됐는지 기존 보고서와 실행 자료를 확인해라.

* 중복·잘못된 행동 거부와 상태 보존
* 턴·사망·승패·연쇄 효과 처리
* 퀘스트·보상 중복 처리
* 저장·상태 복원·API 권한
* 브라우저 없이 실행 가능한 클라이언트 이벤트·연출 큐 처리

미실행 항목은 안전한 테스트 환경에서 수행하고, 환경상 불가능하면 차단으로 기록한다. 브라우저 화면과 애니메이션의 시각적 자연스러움은 계속 미검증으로 남긴다.

## 7. 최종 검증과 반영

추가 수정 후 다음을 실행하고 정확한 명령과 결과를 보고해라.

* typecheck
* 관련 테스트와 회귀 테스트
* 자동 매치
* build
* git diff --check

검증이 통과하면 의도한 변경만 커밋하고 정상 remote·브랜치로 push해라. 기존 사용자 변경과 관련 없는 파일은 포함하지 마.

앞선 조건대로 별도 Render 배포는 하지 않는다. push가 운영 자동 배포를 유발하면 push 직전까지 완료하고 보고한다.

최종 보고는 “실행 성공”, “규칙 정확성 검증 통과”, “UNVERIFIED”, “차단”을 분리하고, 개발 데이터 보정과 실제 런타임 코드 수정을 구분해라. 커밋 해시와 push 여부도 명시해라.

계획 설명으로 끝내지 말고 위 후속 검증과 필요한 수정을 진행해라.
